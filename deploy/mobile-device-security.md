# 手機版（PWA）裝置端資料與裝置管理建議

> **狀態：建議，由導入企業自行評估是否採行。** 系統端能做的已經做完（見〈二〉）；
> 剩下的風險只能靠裝置管理政策處理，而那是各企業 IT 的權責與既有環境決定的事，
> 本文不預設貴司已有或必須導入任何特定產品。
>
> 來源：2026-09-29 手機版安全盤點。

## 一、手機上會留下哪些資料

手機版為了在沒有網路時也能報工，會把部分資料存在手機瀏覽器裡。**這些資料沒有加密。**

| 位置 | 內容 | 什麼時候清掉 |
|------|------|--------------|
| 離線佇列（IndexedDB `mes-offline-queue`） | 尚未送出的報工、上下架、盤點等：派工單號、數量、不良原因、排入者帳號 | 送出成功後標為「已送出」；**登出時**清掉已送出的紀錄。**未送出的會保留**，直到本人登入後送出 |
| 報工草稿（同上） | 填到一半的表單 | 登出時清掉 |
| 派工／機台快取（Service Worker 快取） | 派工清單、機台狀態 | 5／30 分鐘過期；**登入與登出時**清掉 |
| 離線身分（localStorage） | 帳號代號、名稱、角色、廠別（**不含密碼**） | 超過 8 小時失效；登出或伺服器判定登入失效時清掉 |
| 頁面程式與樣式 | 手機版本身的畫面檔案 | 改版時自動更新 |

資料內容屬生產現場的作業資料（派工、數量），**不含密碼、金額、個資**。

## 二、系統端已做的處理

- **竄改無效**：數量、檢驗合格判定、作業員、機台與模具一律由伺服器重新檢查。
  就算有人改了手機上的程式或待送資料，也寫不進不合理的數值或冒用他人名義。
- **換人不代送**：A 離線排入的資料，B 登入後不會以 B 的身分送出，要等 A 登入。
- **換人看不到內容**：首頁的待同步清單只列本人的項目，別人的只顯示筆數。
- **登出前提醒**：登出時先嘗試同步；本人仍有未送出資料時，會詢問是否仍要登出。
- **逾時提醒**：本人有資料超過 24 小時仍未同步時，首頁會提醒聯繫主管處理。

## 三、剩下的風險

未送出的資料以**明文**存在手機瀏覽器裡。能直接讀取或修改的前提是：

- **Android**：開啟「開發人員選項」與「USB 偵錯」，再接上電腦，以電腦版 Chrome 的遠端偵錯開啟。
- **iOS／iPadOS**：在 Safari 設定開啟「網頁檢閱器」，接上 Mac 並信任該電腦。
- 或手機**遺失且未上鎖**，被他人直接操作。

一般使用者在手機上**無法**直接打開開發者工具，所以實際風險取決於「現場手機能不能被開啟偵錯、接上電腦」。

> 為什麼不在瀏覽器裡加密：頁面自己必須能解密才能離線運作，金鑰只能放在同一支手機上，
> 能打開偵錯工具的人就能用同一份程式解密——擋不住上述途徑。
> 改用「每人 PIN 碼推導金鑰」擋得住，但忘記 PIN 時未送出的報工就解不開，等於資料遺失，
> 且離線冷啟動都要輸入 PIN。除非法規或稽核明文要求，不建議採用。

## 四、建議做法（請依貴司環境評估）

以下選項名稱依各 MDM／企業行動管理產品而異，請以貴司實際使用產品的文件為準。

### 4.1 共用的現場手機（建議優先）

| 建議 | 目的 |
|------|------|
| 以 MDM（例如 Android Enterprise 的公司自有裝置模式）**停用開發人員選項與 USB 偵錯** | 關閉讀取／修改瀏覽器資料的主要途徑 |
| iOS 裝置以**監督模式**管理，**限制與未授權電腦配對** | 同上（網頁檢閱器需要配對 Mac） |
| 強制**螢幕鎖定**，並啟用**遺失時遠端鎖定／抹除** | 手機遺失時資料不被直接取用 |
| 限制可安裝的 App、固定使用受管理的 Chrome／Safari | 避免以其他瀏覽器或工具存取 |
| 交班時**登出**（系統會提醒未送出資料） | 讓換人的清理與提醒機制生效 |

### 4.2 個人手機（BYOD）

資料存在個人手機，企業無法強制上述設定。若允許 BYOD，建議至少：

- 以工作設定檔（Work Profile）或同等機制隔離手機版的使用；
- 要求螢幕鎖定；
- 在使用規範中載明「現場作業資料會暫存於手機，離職或換機前須登出並同步完畢」。

### 4.3 不必做的

- **不需要**另外加密手機本機儲存：Android／iOS 在設定螢幕鎖定後，裝置儲存本身即已加密。
  本文的風險是「解鎖後被偵錯工具讀取」，不是「拆機讀取儲存晶片」。

## 五、評估檢核表

- [ ] 現場手機是公司自有、共用，還是個人手機？
- [ ] 是否已有 MDM？能否停用開發人員選項／USB 偵錯（Android）、限制電腦配對（iOS）？
- [ ] 是否強制螢幕鎖定與遠端抹除？
- [ ] 交班流程是否包含「登出」？
- [ ] 貴司資安規範或客戶稽核是否要求「行動裝置暫存資料須加密」？若是，請與我們討論〈三〉所述 PIN 方案的取捨。

## 六、推播的對外連線（伺服器端規範）

> **狀態：規範（必須遵守）。** 與本文〈一〉～〈五〉的裝置端建議不同，這一節是伺服器部署的硬性前提。
> 來源：2026-11-06 推播 SSRF 修正（security-review-20261105 §5 #2），使用者裁決以文件規範處理。

伺服器送出 Web Push 時**不走系統代理**（`UseProxy=false`），也不跟隨轉址：

- 送出前檢查訂閱的網址：只接受 https、443 埠、白名單內的推播服務
  （`fcm.googleapis.com`、`updates.push.services.mozilla.com`、`web.push.apple.com`、`*.notify.windows.com`；
  可用 `WebPush:AllowedEndpointHosts` 調整）。
- 連線時自行解析 DNS，任一位址落在私有或保留網段就拒絕，並**直接連到檢查過的 IP**。
  經過代理的話，實際連線對象是代理而不是推播服務，這道位址檢查就形同虛設，所以刻意不支援代理。

**部署要求：**

1. 應用程式主機必須能**直接**對外連到上述推播服務的 443 埠（防火牆放行對外 HTTPS）。
2. 若貴司網路規定對外一律經 HTTP 代理，**推播會送不出去**：桌機與手機的其他功能都正常，
   只是收不到推播，而且畫面上不會有錯誤，只在伺服器日誌留下「推送失敗」警告。
   請為應用程式主機開放上述網域的直接對外連線，**不要**為此修改程式改走代理。
3. 不得為了測試而把私有網段或內部主機加進 `WebPush:AllowedEndpointHosts`。

**驗收方式：** 部署後在手機首頁按「測試推播」，應立即收到通知。沒收到就查伺服器日誌：
出現 `Push destination…` 或「推送失敗」，代表對外連線被擋或經過了代理。
