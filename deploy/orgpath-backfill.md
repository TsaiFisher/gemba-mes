# 歷史資料 `OrganizationUnitPath` 回填

> **狀態：腳本已備，開發區不執行。** 開發區資料是種子資料，回填與否沒有意義；
> 本文件的目的是讓正式區有一份可直接照做的作業程序。執行時機為
> **P2 檔位（`Features:ReportTools`）上線前**，與 [`file-backup.md`](file-backup.md) 同一個時間點。
> 對應 [`llm-qa-and-report-tools.md`](../.claude/specifications/llm-qa-and-report-tools.md) §8.3 待決 #3／#11，
> 走的是該節「路徑 A（不動 Core）」。

## 一、為什麼要做

[`Data/ApplicationDbContext.cs:186-203`](../Data/ApplicationDbContext.cs#L186-L203) 的資料權限過濾器帶一條 legacy 放行：

```
string.IsNullOrEmpty(CurrentRolePath)
    ? e.CreatedByRoleId == CurrentRoleId
    : (string.IsNullOrEmpty(e.OrganizationUnitPath) || e.OrganizationUnitPath.StartsWith(CurrentRolePath))
```

原註解寫得很清楚：`OrganizationUnitPath` 為空的資料是「DataAuth 啟用前的歷史資料，視為公開」。

在**單據畫面**上，這代表偶爾多看到一筆歷史單，影響有限——所以它至今沒出過事。
在**彙總報表**上，性質完全不同：這批列會被無聲加總進金額。

> **關鍵在於它不會以「錯誤」的形式出現。** 報表跑得出來、數字前後自洽、
> 小計加得起來等於總計。只是那個總計裡混進了不該被這個人看到的歷史金額，
> 而畫面上沒有任何線索。P2 把報表工具化、讓更多人自己排程跑報表之後，
> 這個缺口的曝光面會從「幾個高權限畫面」擴大到「每個排得出報表的人」。

## 二、三個選項

| 選項 | 做法 | 評價 |
|------|------|------|
| **A. 回填（建議）** | 把歷史列的 `OrganizationUnitPath` 補成「建立者角色的組織單位路徑」 | 一次做完，之後所有查詢與報表自動正確，不需要每支工具各自記得防 |
| **B. 工具端排除** | 機密類工具內顯式 `Where(e => !string.IsNullOrEmpty(e.OrganizationUnitPath))` 並標示口徑 | 不動資料，但**每一支新報表都得記得加**，漏一支就破功；且歷史金額直接從報表消失，總計對不上帳 |
| **C. 不做** | 維持現狀 | 只有在盤點結果是 0 列時才成立——那就真的沒事，見第三節 |

**先跑盤點再選。** 如果 `legacy_blank` 是 0，本文件到此結束，選 C 並在此註記日期即可。

## 三、步驟

### 1. 盤點（唯讀，先跑）

```bash
psql -f scripts/orgpath-inventory.sql
```

輸出六段，重點看這三個數字：

| 欄位 | 意義 | 怎麼判讀 |
|------|------|---------|
| `legacy_blank` | 吃到 legacy 放行的列數 | **0 → 選項 C，收工** |
| `fillable` | 其中回填得出路徑的 | 回填一次能解掉多少 |
| `blocked_no_role` / `blocked_role_no_ou` | 回填不出來的，以及卡在哪 | 這批做完仍是缺口，見第五節 |

最後兩段是前置健檢：**「有角色沒掛組織單位」若有結果，先把組織單位補齊再回填**——
否則那些角色建的資料這次會全部落進補不出來的那一堆。

`tables_scanned` 若為 0，代表掃描條件失效（例如 schema 不是 `public`），
那是腳本壞了，不是「沒有問題」。

### 2. 備份

```bash
scripts/backup-db.sh
```

**這一步不能跳過**，理由見第四節「回復」。

### 3. 試跑

```bash
psql -f scripts/orgpath-backfill.sql
```

預設就是試跑：跑完自動 `ROLLBACK`，資料不會變，但會印出**真實的**逐表筆數
（因為它是在交易內真的跑過 `UPDATE` 才回滾的，不是估算）。

筆數應與盤點的 `fillable` 一致。不一致就停下來查，不要往下做。

### 4. 套用

```bash
psql -v apply=1 -f scripts/orgpath-backfill.sql
```

回填規則只有一條，對齊 [`ApplicationDbContext.cs:258`](../Data/ApplicationDbContext.cs#L258)
（`OrganizationUnitPath ??= CurrentRolePath`）：**這筆資料當初若是今天建的，會被寫成什麼，就填什麼。**

腳本是冪等的（條件限定「目前為空」），重跑不會覆蓋已有值的列。

## 四、回復

**只有一條路：從第 2 步的備份還原。**

回填之後，資料庫裡無法再分辨「這一列本來就是這個路徑」與「這一列是剛剛被補上的」——
兩者長得一模一樣。所以沒有「反向腳本」這種東西，也不要試圖用
「路徑等於建立者角色的路徑」反推，那個條件會連正常建立的資料一起清掉。

這就是為什麼第 2 步是硬前置。

## 五、做完之後仍然存在的缺口

### 補不出來的列

`blocked_no_role`（沒有 `CreatedByRoleId`）與 `blocked_role_no_ou`（角色沒掛組織單位）
這兩批**維持空值不動**，繼續吃 legacy 放行。

腳本刻意不去猜——填一個猜出來的路徑進去，比留著一個已知、可量測的缺口更糟：
前者會讓後續所有人以為問題已經解決。

若這批筆數不可忽略，處理順序是：先補角色的組織單位歸屬 → 重跑腳本（冪等）→ 再看殘留。

### 路徑前綴互相包含

過濾器用的是 `StartsWith`，所以組織路徑 `Root/Sales` 的角色會連 `Root/SalesOps`
的資料一起看到。這是既有的過濾器語意、不是回填造成的，
但**回填之後這批歷史資料才真正開始受它影響**（在此之前它們對誰都可見，前綴問題無從顯現）。

盤點腳本最後一段會把有這個特徵的路徑對列出來。有結果的話，要嘛改組織單位命名，
要嘛接受——但要是知情地接受。

## 六、必須事先溝通的一件事

回填會讓可見範圍**收斂**：一批原本全公司都看得到的歷史單據，
之後只有建立者所屬組織單位及其上層看得到。

對平行部門的使用者來說，體感就是「我昨天還查得到的舊單，今天不見了」。
這正是這次要達成的效果，但**如果沒有事先講，它會以客訴的形式回來**。

盤點腳本的 D 段（回填後會落到哪些路徑、各多少列）就是為了這場溝通準備的——
帶著那張表去講「哪些資料會收進哪個部門」，比事後解釋容易得多。

## 附錄：開發區實測（2026-08-13，用來驗證腳本本身）

開發區的資料是種子資料，**下面的數字對正式區沒有參考價值**，
記在這裡是為了留下「這兩支腳本真的跑過、而且結果自洽」的證據。

| 項目 | 結果 |
|------|------|
| 掃到的表 | 35 張（其中 14 張有 legacy 列） |
| `legacy_blank` | 119 |
| `fillable` | 34 |
| `blocked_no_role` | 85 |
| 試跑筆數 | 34（與 `fillable` 相符） |
| 套用後重跑盤點 | `legacy_blank` 119 → 85、`fillable` 0 |
| 冪等驗證 | 第二次 `apply=1` 回填 0 筆 |

套用與冪等驗證是在 `CREATE DATABASE … TEMPLATE "ProjectZ"` 複製出來的暫時庫上做的，跑完即刪。

### 實測帶出的一件事：回填涵蓋率取決於角色有沒有掛組織單位

開發區「前置健檢一」會列出 6 個沒掛組織單位的角色（`SALES`／`WH`／`PUR`／`FIN`／`OP`／`3`）。
**那不是設定錯誤，是 [`RolePermissionSeeder`](../Services/RolePermissionSeeder.cs) 的刻意設計**——
只有 view-all 角色（`1`／`HQMGR`／`MGR`）指派到根 OU，其餘角色 `CurrentRolePath` 為空，
過濾器對它們走的是另一條分支（`CreatedByRoleId == CurrentRoleId`，只看自己角色建的）。

連帶結果：**這些角色建立的資料天生回填不出來**——開發區 85/119 卡在這裡。
正式區若已經把組織架構導進去、角色也實際掛上單位，比例會完全不同。
所以第三節第 1 步不能跳過：**涵蓋率是量出來的，不是推出來的。**

這同時說明為什麼選項 B 不能當唯一手段——殘留必然存在，
每支報表各自 `Where` 排除只是把「看得到不該看的」換成「總計對不上帳」。
