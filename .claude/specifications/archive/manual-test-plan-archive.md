## 0. 兩個前置結論（規劃前必讀）

### 0.1 目前已測範圍全部落在「數量流」，三條主資料流都停在金額認列之前

| 資料流 | 已測（數量流） | 未測（金額流） |
|---|---|---|
| P2P 採購付款 | PR → PO → GR → 庫存上架 | GR/IR 暫估 → AP 發票 → 付款 → 傳票 |
| O2C 銷售收款 | SO 訂單 | 出貨 → 扣庫存 → AR → 收款 → COGS 傳票 |
| Plan-to-Produce | MRP → 排程 → 工單 → 開工/報工 | 備料領料 → 完工入庫 → 工單成本 → WIP 結轉 |

**為什麼這件事要優先處理**：AVCO 平均成本是逐筆累積的。GR 階段若成本寫錯，畫面不會有任何異常，
但之後每一張出貨的 COGS、每一張工單的實際成本都會連鎖偏掉，要到月結損益對不起來才會發現——
屆時前面累積的測試單全部作廢重來。故規劃原則是**縱向打穿一條流到傳票，再回頭加寬**，
而非繼續橫向鋪模組。

### 0.2 簡化模式目前是「全系統單一開關」，無法按廠別設定

這是本次查證發現的架構落差，直接影響「部分廠別使用簡化模式」這個需求：

| 查證項目 | 事實 | 位置 |
|---|---|---|
| 參數表結構 | `SystemParam` 主鍵**只有 `Key`**，類別註解明寫「系統全域參數（KV 形式，非廠別隔離）」 | `Models/SystemParam.cs` |
| 讀取介面 | `ISystemParamService.GetAsync(string key)` **無 `plantId` 參數**，且有 `IMemoryCache` 全域快取 | `Services/SystemParamService.cs` |
| `inv_simplified_mode` 讀取點 | **18 處**（PUR 7、INV 4、ORD 4、MFG 1、Filter 2） | 見下方清單 |
| `mfg_simplified_mode` 讀取點 | 1 處，已收斂於 `IMfgSimplifiedModeService`（單一判定來源，設計良好） | `Modules/MFG/Services/IMfgSimplifiedModeService.cs` |
| 文件與實作不符 | `ProjectZSystemParamKeys.MfgStandbySchedulable` 註解寫「支援廠別隔離」，但實際呼叫 `GetAsync(key)` 為全域值 | `Models/ProjectZSystemParam.cs:19` vs `Modules/MFG/Services/SchedulingEngine.cs:100` |

**結論**：現況下設定 `inv_simplified_mode=true` 會讓**所有廠別**同時切換，做不到「A 廠簡化、B 廠完整」。

**對測試規劃的影響（三選一，需先決策）**：

- **方案 A（建議）**：先做廠別覆寫層再測。`SystemParam` 主鍵改 `(Key, PlantId)`，`PlantId` 為 null 代表全域預設，
  `GetAsync` 增加 plantId 多載並以「廠別值 > 全域值」解析，快取鍵一併帶廠別。
  改動集中在參數層，18 個讀取點多數只需換多載。**在此之前不要開始測簡化模式**，
  否則 Wave 1–5 得在切換全域開關後整批重測。
- **方案 B**：先照全域完整模式跑完 Wave 1–5（本文件主線），簡化模式列為後續獨立測試批次，
  待廠別覆寫層完成後再單獨驗證差異路徑。
- **方案 C**：若上線初期所有廠別一致為完整模式，簡化模式暫不測，但需在專案待決項登錄，避免上線後才發現不支援。

#### ⑥ 讓 P1／P2 真的能排產

①～⑤ 補完之後兩廠只能做庫存與進銷貨。要真的排產，先撞到一個架構事實：

> **`Products` 是全域主檔且只有一個 `RoutingId`，而 `Routings` 是廠別主檔、

#### ⑪ 產品類別的收入科目改為 4100（2026-09-02）

`RM`／`WIP`／`FG` 的 `RevenueAccountCode` 由 `4110 其他營業收入` 改為 **`4100 銷貨收入`**。

理由是**同一筆營收不該落在兩個科目**：這組科目只用於**手動發票**
（`ARInvoiceService.BuildManualJournalLinesAsync`），而正常的出貨開票走
`StandardAccounts.SalesRevenueCode` = `4100`。同一個成品走出貨開票進 4100、
走手動開票進 4110，5-6 報表對帳只要兩條路徑都有單，數字就對不起來——
與 §12.7 才剛修掉的毛利表缺陷是同一種形狀（兩腿取不同批單據）。

**費用科目：2026-09-02 定為 `5900 其他營業費用`——這是「經過考慮的預設值」，不再是佔位值。**

理由不是「找不到更好的」，而是**在這條路徑上，一個具體但錯的科目比一個籠統但誠實的科目更糟**：

- 手動 AP 發票**依定義就是不走存貨的那條路**（正常進貨是 GR 借 1401／貸 2152，
  再由發票沖 2152），所以它認列的本來就是「沒有進存貨的支出」；
- 若改填一個具體科目（例如 `5001 銷貨成本`），等於主張這些支出都是已售商品成本——
  對原物料而言那是**錯的**，而且錯得很難發現；
- `其他營業費用` 沒有主張任何東西，它就是「雜項」，與這條路徑的語意相符。

🚨 **會讓這個預設值失效的唯一觸發條件**：如果開始拿手動 AP 發票補「**該進存貨但沒走 GR**」
的原料進貨。屆時**正確的修法不是換一個費用科目，而是改走 GR 路徑**——
這個欄位的分錄寫死借費用科目，不管填什麼都會讓存貨少計。
換句話說，看到有人想把這個值改成 `1401`，那就是走錯路的信號。

⚠️ 上線前業主仍應確認一次，但**驗收不再被它擋住**，且已不是「開發隨便挑的」。

`SA1103` 在 `WIP-ADM-01` 是**零庫存**（整個 WIP 儲位都空的）。

所以 Wave 2 必須**先跑一張 `SA1103` 的工單**，而且——

> **`SA1103` 完工入庫時，倉別必須手動改成 `WIP-ADM` / `WIP-ADM-01`。**

補了 ⑫ 的預設值之後，這一格會**預先填成 `F001` / `F001-1`**，直接按確定就會把 `SA1103`
收進成品倉。接著跑 `PA1103` 時，後沖去 `WIP-ADM-01` 找不到料判可用量不足，
而**後沖包在完工入庫的同一個交易裡，整張 `PA1103` 工單就再也無法入庫**。

⚠️ 這正是 2-9 條文早就警告過的形狀，但那裡把它寫成「分倉部署的**上線前檢查項**」，
沒有寫成 Wave 2 的**執行順序**——測試員照著步驟表跑，不會知道要在 2-5 手改倉別。
已同步補進 §5.1 的 2-5。

**為什麼仍然選擇補這個預設值**：不補的話預設空白、每次強迫手選，確實比較不容易選錯，
但那是**副作用擋下來的，不是設計擋下來的**，而且代價是 2-5 少驗一層。
補了預設值再用文件擋陷阱，才是把兩件事各自放在該放的地方。

#### ⑬ 開跑前的資料 pre-flight：Wave 1／2／3 的成本腿會不會是假的（2026-09-02）

App 起來之後，用與 ⑫ 同樣的方式把 Wave 1／3／4／5 的資料前置也查了一遍。以下按「會不會讓測試恆真」排序。

**先更正我自己的一個誤判**：查到 `Inventories.UnitCost` 幾乎全是 0 時，我一度以為是上架沒更新移動均價的缺陷。
**不是。** `ProductCategories.CostMethod` 分兩套——**`RM`＝Fifo(2)**，`FG`／`WIP`＝MovingAverage(1)。
原物料的成本存在 `InventoryCostLayers` 的層裡，`Inventories.UnitCost` 對 FIFO 品項本來就不是計價來源。

（2026-07-14～07-22）。`InventoryPostingService` 只在「入庫**且**帶單價」時更新計價
（`direction == 1 && unitPriceLocal.HasValue`），庫存調整沒帶單價就不更新——
所以這批料進了倉、成本是 0，而且**帳面上完全看不出來**。

SELECT je."JournalId", je."SourceDocType", je."SourceDocId",

| --- | --- | --- |
| 訂購 100、發料 100、分兩批各收 50（零損耗） | 0 | 2,700（第一批 1,350 ＋第二批 1,350） |
| 訂購 100、發料 110、分兩批收 60＋40 | 135 | 3,270（1,335 ＋ 1,935） |

第二列的加工費總額只有 2,500——廠商做完了還要倒貼。批數越多罰得越兇，而且不會回頭修正。

**在外原料的第二個破口**：委外發料屬 Outsource 類，庫存數量出而總帳不動，
料的價值一直留在存貨科目 1401；收貨時併回成品的只有**理論消耗**（收貨量 × BOM），
被報廢掉的差額（上表第二列是 300 元）既沒進成品也沒人賠，就永久留在 1401。
每一張傳票都平衡，§3.3 稽核只驗數量又只抓負餘額，所以完全沉默。

**修法**（三件事合成一支 `IOutsourceReceiptSettlementService`，因為它們是同一筆錢的兩個去處）：

1. **粒度改累計**。中間批不扣款，只把理論消耗併回成品；結案批以「累計收貨量 vs 淨發料量」
   一次算清，並把剩下的在外原料餘額一次掃進成品（扣掉廠商要賠的那一份）。
   發料量改為 OO 減 OR 的**淨額**，與 §3.3 稽核同口徑。
2. **結案批的判定**。收足訂購量自動結案；短交要結算則需人工勾選收貨單上的
   「本單為最後一批」——系統分不出「還在加工」與「已經報廢」，這一刀只能由人來下。
   不勾也不會有帳務破口，餘額留著等下一批，代價只是那筆料錢晚一點才有落點。
3. **扣款改貸存貨**。收貨確認時另過一張 借 2152／貸 1401 的分錄。
   `APInvoiceService` 讀的是「這張收貨單實際貸記了多少 2152」，補進去之後它算出來的差異
   自然是 0，兩端不必各自重算（原本落在 5151 的那筆就此消失）。

修正後，走完全程的恆等式是：**發出去的料價值 = 成品吸收的 + 廠商賠的**，
於是總帳存貨科目淨額 == 庫存明細帳合計。允收範圍內的正常損耗是**產品成本**故併入成品，
但只會攤在結案批身上（已過帳批次的成本不能回頭改寫），該批單位成本會比前幾批高——
這是刻意的取捨，總額對、分布粗。

**看報表時要知道的事**：結案之後「在外原料餘量」不會歸零，剩下的正是被報廢掉的數量。
價值已經結清（進了成品成本或由廠商賠），數量欄留著是因為那批料本來就沒有回來——
§3.3 稽核只抓負餘額，正餘額在這裡是正常的。

**仍未收**：完全模式（非簡化）的收貨確認不過帳庫存，`PostLineDetailRequest` 也沒有
`CarriedInCost` 欄位，所以在外原料在完全模式下根本沒有併回入口；
以及短交後沒有人勾結案的委外單，料錢會一直掛在在外餘額——這件事在委外進度畫面看得到，
不算靜默，故不另加稽核。

**出場條件**：一張工單能從核准走到完工入庫且成本可追溯回領料與報工；委外流程至少完整跑通一輪，
且**分批收貨至少跑過一次**。
✅ **出場條件已達成**（2026-09-24 查證開發庫）：`OP-2609-00002` 分兩批各收 4 個、兩批皆已過帳，
且兩批的 `CarriedInMaterialCost` 分別是 240 與 300（**不同**，正是結案批吸收正常損耗的形狀）。

### 6.2 對帳點

依《對帳規格》§1.2。其中最關鍵的一條硬對帳：

```sql
-- 出貨的庫存扣減成本 vs 傳票 COGS 借方（差額應在容忍值內）
-- COGS = 5001（StandardAccounts.Cogs，程式常數）
--
-- ⚠️ SourceDocType 是 'INV' 不是 'GoodsShipment'：庫存過帳的自動分錄一律以
--    InventoryPostingService.InvDocType（＝'INV'）寫入，單號才是出貨單號。
--    寫成 'GoodsShipment' 會得到 cogs_debit = NULL，看起來像「傳票根本沒開」。
--    （2026-09-04 Wave 3 實測時發現原文寫錯。）
SELECT sm."DocNo",
       SUM(sm."TotalCost")                     AS stock_cost,
       (SELECT SUM(jl."Debit")
          FROM "JournalEntries" je
          JOIN "JournalLines" jl ON jl."JournalId" = je."JournalId"
         WHERE je."SourceDocType" = 'INV'
           AND je."SourceDocId"  = sm."DocNo"
           AND jl."AccountCode"  = '5001') AS cogs_debit
FROM "StockMovements" sm
WHERE sm."DocNo" LIKE '<出貨單號前綴>%'
GROUP BY sm."DocNo";
```

若這裡對不起來，**問題多半不在 Wave 3，而在 Wave 1 或 2 的成本寫入**——這正是把成本鏈排在前面的理由。

### 6.4 銷退入庫計價（3-6 的實測結果）

銷退單上**沒有成本欄位**——畫面帶過來的是售價，所以退回來的貨要用什麼成本入庫，
只能由系統自己決定。原本的實作直接把銷退單價（＝售價）當入庫單價，一次做錯三件事：

1. 存貨科目與庫存明細帳**一起**被灌成售價（兩邊一致地錯，任何對帳都對不出來）
2. 反向沖回的銷貨成本大於當初認列的銷貨成本，毛利虛增
3. 移動平均被汙染，**之後每一次出貨**的成本都跟著錯——錯誤會一直擴散下去

實測（成本 120／售價 300，出 40 退 10）：入庫單價 300，庫存均價從 120 變成 145.71。

**沒有任何既有防線會叫**：兩張傳票各自借貸平衡（只是把錯的數字寫進去而已），
`INV_ROLLFORWARD` 是數量型稽核而數量完全正確，§6.2 那條 COGS 硬對帳只看出貨側。

已修正：入庫成本改取**原出貨庫存異動實際扣掉的單位成本**（`SalesReturnCostBasis`）。
取異動而不是「當時的移動平均」——均價是全廠、隨時在變的值，事後重算回不到出貨當下那個數；
異動列記的是那一次實際扣掉多少，是唯一的事實。未連結來源出貨的手工退回行取現行單位成本
（該路徑不動移動平均，是無從得知原始成本時最不傷害既有計價的做法）。

修正是**forward-only**：已過帳的傳票不能改寫。既有資料靠新增的第 17 支稽核
`SALES_RETURN_COST_DRIFT` 逐筆列出，已掛進 `RunAllAsync`，故未清乾淨之前關不了帳。

### 6.5 外幣銷售的匯率型別（3-7 的實測結果）

匯率有買匯與賣匯兩種，程式的預設值是 **Buy**（`CurrencyService.GetRateAsync`）。
銷售鏈每一段都明寫 `RateType.Sell`——銷貨訂單、出貨單、銷貨退回、AR 收款都是——
唯獨**開票**（`ARInvoiceService.GenerateFromShipmentAsync`）沒有指定型別，退回預設的買匯。

後果：同一筆銷售有兩個本幣金額。出貨單畫面上的本幣合計是賣匯換的，
帳上的應收帳款、營收、銷項稅是買匯換的。以 Wave 0 補建的匯率（買 31.20／賣 31.70）
計算，差距約 1.6%，而且**永遠不會歸零**。

為什麼沒有任何既有檢查會叫：差額不會留在應收——收款當下的匯兌損益會把它整個吸收掉。
於是總帳每張傳票都平衡、應收科目結清為 0、`AuditJournalBalance` 乾淨，
只有「營收金額」與「出貨單本幣合計」是錯的，而這兩個數字沒有任何自動檢查在比。

已修正：開票的匯率改為**沿用出貨單存檔當下鎖住的那一個**（出貨單的
`ResolveLineRatesAsync` 已用後端權威賣匯覆寫並寫進明細），而不是重查一次。
沿用另外解掉一個時序問題：存檔到確認之間若有人補了或改了當日匯率，
重查會取到與出貨單不同的值。明細沒有匯率時（舊資料）才退回查詢，且指定 `RateType.Sell`。

> ⚠️ 既有的 `P2PForeignCurrencyFlowTests` 把買匯與賣匯設成同一個數字，
> 所以「取錯匯率型別」這一類缺陷在它那裡完全看不見。
> `O2CForeignCurrencyFlowTests` 四個匯率互不相等（出貨日買 30／賣 31、收款日買 32／賣 33），
> 任何一段取錯型別或取錯日期都會產生獨一無二的錯誤金額。

與 W4-F7（ERP 拋轉）、W4-F13（期初前出貨）是同一種形狀，
訊息上寫著「請另開折讓單」而系統裡根本沒有折讓單這種東西。

新增 **銷貨折讓單 `ARCreditNote`** 與 **進貨折讓單 `APDebitNote`**（互為對稱）。

**形態選擇（已裁決）**：獨立單據 + 沖抵原發票，**不是**負向發票。

| | 獨立折讓單（採用） | 負向 AR／AP 發票（否決） |
|---|---|---|
| 子帳 | 累加 `ARInvoice.CreditedAmount`，未結餘額＝總額 − 已收 − 已折讓 | 多一筆負數發票 |
| 帳齡 | 原發票餘額直接反映，不必改任何報表 | 客戶決額正確但拆成兩行 |
| 風險 | 影響面收斂成一個**可以 grep 的欄位** | 負數會流進每一支假設「金額為正」的邏輯（`Qty > 0` 驗證、`Received` 的判準 `ReceivedAmount >= TotalAmount`——負數發票一生下來就是已收、核銷上限、帳齡分帳），而且**每一處都是靜默壞掉** |

**分錄與 Open 發票的既有回沖完全相同**，是刻意的：

| | 借 | 貸 |
|---|---|---|
| 銷貨折讓 | 4100 銷貨收入（淨）＋ 2155 銷項稅額（稅） | 1170 應收帳款（含稅）|
| 進貨折讓 | 2100 應付帳款（含稅） | 2152 進貨暫估應付（淨）＋ 1155 進項稅額（稅）|

同一件經濟事實（貨退回來了）不該因為「當時收款了沒」而落到不同科目——
那會讓損益表上的銷貨收入依客戶的付款速度而變動。
AP 側的貸方是 **2152 而不是存貨**：退貨過帳當下已經貸過存貨、借過 2152 了。

**流程**：退貨過帳 → 有缺口就**自動產生草稿**（四個退貨入口都呼叫，產生器冪等，
唯一索引 `(SourceDocType, SourceDocId)` 是最後一道）→ 訊息直接報出折讓單號 →
人到「銷貨／進貨折讓單」畫面確認 → 沖抵原發票未結餘額 ＋ 產生分錄 → 稽核那一筆消失。

> **草稿刻意不讓閘門放行。** 稽核只認 `Posted`——草稿還沒沖任何東西，錢還掛在帳上。
> 若自動產生草稿順手把稽核關掉，這個閘門就等於自己把自己拆了。

**畫面刻意沒有新增與編輯**：每一個數字都來自「哪一張退貨單、退了哪一張發票的哪一行、
退了多少、原單價多少」。開放手鍵等於讓人折出與退貨量對不上的金額，
而那正是稽核在比的東西——手鍵的折讓沖不掉稽核，只會讓帳更難對。

#### 寫測試時當場推翻的一個設計

第一版把上限守成「折讓不得超過未結餘額」，被
`ConfirmingTheCreditNote_ClosesTheGap_AndClearsTheAudit` 當場擋下：
**發票已全額收款時未結餘額是 0**，而那正是這張單存在的情境——客戶付了錢又退貨。
擋掉它等於宣告「已付清的發票不能退貨」。

折讓後應收出現貸餘（公司欠客戶）是**正確的結果**，後續由退款或抵下一張發票處理。
上限改守**數量**：累計折讓量不得超過發票明細開立量——那也正是稽核在比的東西。
草稿產生時已上限過一次，確認時再驗一次（草稿到確認之間可能有另一張折讓單先過帳）。

### 7.3 盤點與作廢的實測結果（4-2／4-7／4-8）

以下三件都是照著作業書逐項寫自動化測試時撞出來的，不是推測。

#### 一、盤點結帳的異動類別從來沒被種進系統（乾淨部署必壞）

`InventoryCountController.Close` 硬寫 `TypeCode = "IC"`，而系統種子
（`ApplicationDbContextExtensions` 的 `InventoryTransactionType` HasData）**只有 IA 庫存調整，沒有 IC**。
過帳第一行就是 `FindAsync("IC")`，找不到即丟「找不到異動類別 IC」，
於是**乾淨部署的盤點只要盤出任何差異就結不了帳**；零差異反而結得掉（沒有明細要過帳）。

之所以躲了這麼久：`Postings/InventoryCountPostingResidueTests` 自己補了一筆 IC 進共用測試庫
（`if (!Any) Add(...)`），而測試庫是所有測試共用又不清主檔的，補過一次就永遠在。
那支測試因此一直是綠的，而且是**假綠**——它驗證的是「補了主檔之後會動」，
不是「這個系統會動」。已把該段改成斷言「IC 必須來自系統種子」，並補上
`20260827071932_INV_SeedInventoryCountTransactionType`。

> 同型陷阱值得記著：**測試自己補系統主檔，等於把部署缺口從測試視野裡刪掉**。
> 補的若是業務資料沒問題，補的若是「本來就該隨系統出貨」的種子，那就是在掩蓋缺陷。

#### 二、盤盈被當成進貨，貸進「進貨暫估應付」

`BuildJournalLines` 的對方科目是 `(方向, 業務類別)` 的比對，入庫方向除了銷貨退回之外
一律落到 `(1, _) => 2152 進貨暫估應付`。盤點結帳走的就是入庫方向，於是：

| | 原本 | 現在 |
|---|---|---|
| 盤盈 | 借 1401 存貨 ／ **貸 2152 進貨暫估應付** | 借 1401 存貨 ／ 貸 **4210 存貨盤盈** |
| 盤虧 | 借 5210 報廢損失 ／ 貸 1401 | 借 **5220 存貨盤損** ／ 貸 1401 |

盤點多出來的貨沒有供應商、沒有人會來請款，掛進 2152 等於在負債裡長出一筆
AP 端根本不知道、永遠沒人來沖的錢，每盤一次多一筆且不收斂。
實測（三個料件各期初 100，盤盈 10 × 40 元）：2152 從 −7,700 被推到 −8,100。

順帶修掉一個沿路掉件：調整單自己的 `TypeCategory` 預設就是 `Adjustment`，
但 `Close` 建過帳請求時沒往下傳，庫存異動與分錄看到的是 `null`——
所以連「盤點是調整」這件事在過帳層都是不知道的。現在一路傳到底，
手動庫存調整單（IA）也一併走同一組科目。

盤虧與報廢分開列帳是刻意的：報廢是「知道是哪一批、為什麼壞」的主動處分，
盤損是「帳實不符、原因不明」的被動認列，追查的對象與管理意義都不同。

#### 三、付款／收款單作廢完全沒有回沖傳票

這是三件裡最嚴重的一件，而且是在寫 4-2 的「部分付款」情境時順手撞到的。

`FinPaymentService.VoidAPPaymentAsync` / `VoidARReceiptAsync` 做了三件事：
回補發票的已核銷金額、回補銀行帳戶餘額、把單據標成 Void——**總帳一個字都沒動**。
確認付款時那張「借 2100 應付帳款 ／ 貸 1130 銀行存款」就這樣永遠留在帳上：
子帳說錢沒付、負債還在，總帳說錢付了、負債沒了，兩邊從此各說各話且不會收斂。

銀行餘額被回補這件事讓它更難查——**現金對得起來，只有總帳的 1130 對不起來**。
現已比照 `APInvoice-Void`／`INV-Void` 的口徑補上 `APPayment-Void`／`ARReceipt-Void` 回沖。

#### 四、部分付款的發票可以被作廢（守門少了一個狀態）

`APInvoiceService.VoidAsync` 只擋 `Paid`，`ARInvoiceService.VoidAsync` 只擋 `Received`。
但作廢的回沖是把**整張**認列分錄借貸對調（借 2100 全額），
已付的那一筆自己的 借 2100 還留著，兩筆借方加起來超過原本的貸方——
應付帳款變成借餘：錢付出去了，帳上卻沒有任何負債對得上，再也沒有東西會來沖它。
AR 的收款端完全對稱。

守門自己的錯誤訊息就寫著「請先沖銷付款」，意思顯然是「只要核銷過就得先沖掉」，
少的只是 `PartialPaid` / `PartialReceived` 這個狀態。已改為
「只要 `PaidAmount`／`ReceivedAmount` 大於 0 就擋」，並更正
`IAPInvoiceService.VoidAsync` 上寫著「僅 Open/PartialPaid 可作廢」的註解。

  現況是「手動發票在子帳看得到、總帳看不到」，作廢時也因為找不到原分錄而自然無事發生（一致，但不完整）。
  要收這個缺口得先有「品號／類別 → 費用科目」的對應設定，屬於規格層面的新增，不是修 bug。

### 7.4 跨廠調撥的價值搬運（4-9／4-10 的實測結果）

規格（`inventory-advanced.md` §2-2、`inventory.md` 四-C）從頭到尾只描述**數量**與成本傳遞，
沒有任何一段提到分錄。實作照著做了，於是兩段式過帳（XP 撥出 → XI 撥入）完全不入總帳。
但 `JournalEntry.PlantId` 是有廠別的，全站的稽核與對帳也都逐廠在跑，
所以「每一廠的存貨科目等於該廠的庫存明細帳」是這個系統確實在主張的不變量。

實測（甲廠 100 個 @ 40 元，撥 30 個給乙廠）發現兩個缺陷：

| | 現象 | 為什麼沒人叫 |
| --- | --- | --- |
| 價值沒跟著走 | 甲廠貨走了、存貨科目沒動（仍 4,000，明細帳只剩 2,800）；乙廠貨到了、存貨科目沒動 | 兩廠剛好相抵，**全公司層級看起來是對的**，逐廠看才差一筆；每調撥一次就多差一次 |
| 目的廠單價是 0 | 乙廠收到的 30 個在庫存明細帳上是**零元** | `UpdateQtyAsync` 只改數量。同廠調撥沒這問題（新開儲位會承接該廠現行單價），但目的廠通常根本沒有這個品號的庫存。之後從乙廠出貨 COGS 取 0，毛利虛增，而數量完全正確故 `INV_ROLLFORWARD` 與傳票平衡都不會叫 |

**修法**：

1. 新增清算科目 **1450 廠際調撥往來**。撥出：甲廠 借 1450／貸 1401；撥入：乙廠 借 1401／貸 1450。
   在途期間甲廠的 1450 就是在途存貨；收貨後兩廠一正一負，即甲對乙的往來餘額，**全公司合計恆為 0**。
   帳表無科目主檔（分錄的科目是字串），故不需要建檔或種子。
2. `PostCrossPlantReceiveAsync` 補上成本承接，來源是 XP 異動的凍結成本。
   **必須排在 `UpdateQtyAsync` 之前**——移動均價是以「尚未加上本次入庫量」的在手量重算的。
3. 作廢回沖改為逐（單號, 廠別）沖銷，兩廠各自回沖自己那一腳；同廠調撥本來就沒有分錄，自然是 no-op。

**順帶修掉的**：沖銷分錄的重複防護原本是「已有反向分錄就整個跳過」。
在只能作廢一次的單據上等價，但跨廠調撥的「撤回發出」可以退回草稿再確認，
於是 確認→撤回→確認→撤回 的第二圈完全不回沖，第二次確認的分錄永遠留著。
改成回沖「原分錄 − 已沖銷」的**淨額**之後每一圈都回到原點，重複作廢也照樣是 no-op。

### 7.5 撤回還量與成本層日期（2026-09-07，W4-F14 的延伸）

4-10 的循環測試把「作廢沖銷的**傳票**每一圈都乾淨」釘住了，但沒有問
**成本層**每一圈是不是也回到原點。實測 ADM／MAF1102（XP-2609-00004
確認→撤回 共三圈）發現不是。

#### 一、撤回是另建一層，不是還回被扣的那一層（W4-F14）

`ReverseCostAsync` 的 FIFO 分支原本直接 `AddLayerAsync` 把數量補回去。
數量與價值總額都對——所以 `FIFO_LAYER_QTY_MISMATCH`、`INV_ROLLFORWARD`
與借貸平衡**四支稽核全部不會叫**——錯的是**層齡**：

| | 原層（7/22 進，@300） | 撤回產生的層 |
|---|---|---|
| 撤回前 | 305 | — |
| 三圈之後 | 290 | 三層各 5，`ReceiptDate` 皆為撤回當天 2026-09-07 |

原層被扣掉的 15 個，變成三層排在 9/3 進的 @100 那兩層**後面**。
下一次領料會先領走便宜的 9 月料，把 7 月的貴料永遠壓在底下——
FIFO 的成本流從此與實際進料順序脫節，而且沒有任何一支稽核看得到。

**修法**：新增 `InventoryCostLayerConsumption`（消耗明細），
`ConsumeLayersAsync` 每從一層扣一次就記一列（層 Id、單號、數量、單價、消耗日），
`RestoreConsumedAsync` 依單號回查、**後扣的先還**（與消耗順序對稱），
把數量加回**原層**。舊單據查無消耗紀錄時回傳 0 而**不擲錯**，
由呼叫端補一層作為退路——否則修正上線之後，修正前的單據會全部變成不可作廢。

#### 二、成本層的日期一律是建層當天，不是單據異動日（同批修）

`AddLayerAsync` 原本寫 `IDateTimeService.GetLocalDate()`。
`ReceiptDate` 全站只有兩個讀取點——`ConsumeLayersAsync` 與 `RemoveLayersAsync`
的 `OrderBy(ReceiptDate).ThenBy(Id)`——沒有任何報表或稽核讀它。
於是實際行為一直是「**依過帳順序** FIFO」：所有層的日期都等於過帳那天，
排序整條退化成 `ThenBy(Id)`，答案剛好對。

兩者只在**倒填單據**時分岔。異動日欄位是開放的 `<input type="date">`，
沒有 `max`，只被期間鎖擋，所以補單、月初補 7 月的料都做得到；
補進來的舊料會被排在已在庫的新料後面，這一次領料就領到錯的那一層，
發料成本、在製成本、結轉的銷貨成本跟著全錯，而數量完全正確、傳票完全平衡。

**修法**：`AddLayerAsync` / `ConsumeLayersAsync` 改為**由呼叫端傳入業務日**
（`receiptDate` / `consumedDate`，刻意不給預設值，漏傳就是編譯錯誤），
呼叫端一律傳 `MovementDate`。同時把 `IDateTimeService` 從
`InventoryCostLayerService` 的建構式**整個拿掉**——這一層寫進去的每一個日期
都是「某次過帳的業務日」，沒有任何一個該由它自己決定。
拿掉依賴讓「本層自己產生日期」成為結構上的不可能，不是靠註解約束。

> 時區保證因此**上移**了：原本 `InventoryTimezoneOperationTests` 斷言
> 遠東／遠西兩廠同一時刻建的層會差一天（＝各自跟著廠時區），
> 現在斷言的是**兩廠拿到同一個日期**，且等於單據上的異動日。
> 保證沒有變弱，只是移到「產生業務日」的那一層（單據的 `MovementDate`）去做。

### 7.7 併發過帳：擋住第二個人的有兩套機制，覆蓋面不一樣（2026-09-07）

4-11 原本被記成「由既有測試涵蓋」。逐支看過之後不成立——全庫七支並發測試
（`ScrapDocConcurrencyTests`、`InvDocHeaderXminTests`、`CrossModuleConcurrencyTests`…）
模擬並發的方式一律是**手寫欄位**：

```csharp
sA.Status = DocStatus.Posted;  await dbA.SaveChangesAsync();
sB.Status = DocStatus.Posted;  await Assert.ThrowsAsync<DbUpdateConcurrencyException>(...);
```

那證明的是「xmin 這個機制會擋」，不是「**過帳這條路**擋得住」。中間隔著三件事：
控制器有沒有把表頭追蹤載入（`AsNoTracking` 會讓 xmin 根本不進 UPDATE 的 WHERE）、
`catch (DbUpdateConcurrencyException)` 有沒有落在真的會拋的那一段、
以及**被擋下的那一方有沒有留下殘留**——第三件才是 §7.1 那句
「重點不是有沒有跳錯誤訊息，而是擋下之後資料庫乾不乾淨」在問的。

#### 一、寫下去才發現：是兩套機制，不是一套

| 機制 | 在哪 | 覆蓋範圍 |
|---|---|---|
| ① 冪等性守門 | `PostDocSimplifiedAsync` 開頭查 `StockMovements` 有無同單同行同類別的異動，有就丟「禁止重複過帳」 | **只有這一處**（全庫僅此一段）。報廢／調整／借出／樣品／委外領料／重工領料等走簡化過帳的單據 |
| ② 表頭 `xmin` | 收尾 UPDATE 帶 `WHERE xmin`，後到者 0 列即拋 `DbUpdateConcurrencyException`，控制器 catch 成 400 | 9 支 INV 單據表頭 |

**移倉與跨廠調撥走的是 `PostSamePlantTransferAsync`／`PostCrossPlantShipAsync`，
完全沒有①，只剩②。** 所以兩條路要分開測——只測報廢單的話，
「②那個 catch 是不是死碼」根本不會被碰到。

> 實測順序就是這樣走出來的：報廢單那支寫完先做突變，把
> `catch (DbUpdateConcurrencyException)` 整段移除，**測試照樣綠**——
> 因為擋住 B 的從頭到尾是①，不是②。這才發現要補移倉那一條。

#### 二、測試

`Flows/ConcurrentPostingFlowTests`（2 支）。兩個 scope、兩個 DbContext，
**兩邊都在任何人送出之前就載入了同一張草稿單**（EF 的識別解析會讓 `Confirm` 內部的
查詢回傳已追蹤的舊快照，而不是覆寫成資料庫的新值——這正是現場「兩個人各自開著同一張單」
的樣子），然後一前一後真的呼叫控制器的 `Confirm`。

| 測試 | 走哪條路 | 斷言 |
|---|---|---|
| `TwoUsersConfirmingTheSameScrapDoc_SecondIsBlockedByIdempotencyGuard` | `PostDocSimplifiedAsync` | 訊息含「禁止重複過帳」；在手量只扣一次、庫存異動只有一筆、傳票不重複、單據狀態只前進一次；孤兒過帳／庫存捲動／重複傳票三支稽核對這張單皆乾淨 |
| `TwoUsersConfirmingTheSameTransfer_SecondIsBlockedByXmin` | `PostSamePlantTransferAsync` | 訊息**必須等於**在地化的 `ConcurrencyConflict`（這條路沒有①，擋下來的只可能是②）；貨只搬一次、WP/WI 各一筆 |

失效形狀：兩邊的狀態守門都看到 Draft（各自的快照都是過帳前的），於是兩邊都走進過帳，
庫存被扣兩次、異動兩筆、傳票兩張，而**兩邊畫面都顯示成功**。
數量會少兩倍，但每張傳票都平衡、庫存捲動也自洽（異動與在手量是一起被扣兩次的），
沒有任何一支既有稽核比得出來。

> **兩支各自做過突變驗證，且打掉的是各自依賴的那個機制**：
> 把①改成 `if (false)` → 報廢那支紅；把移倉控制器的並發 catch 移除 → 移倉那支紅。

**出場條件**：11 項全通過，且每一項擋下後皆確認無過帳殘留。

### 8.1b 列印的合計不是上面那一欄的合計（5-9，2026-09-07）

§14.6 早就寫著「版面只能人眼看，但**金額一致性可以斷言**（產出後比對數字），尚未做」。
做起來之後第一支就紅了，而且在 dev 庫的真實單據上驗得到。

**缺陷**：六張單據（銷貨訂單／出貨單／銷貨退回／採購單／進貨單／進貨退出）的表頭
`TotalAmount` 一律是**本位幣**——模型註解逐字寫著「本位幣總金額（各明細 AmountLocal
加總）。明細可為不同幣別，故表頭一律以本幣合計」。而列印畫面的明細欄印的是
`l.LineAmount`／`l.TotalAmount`——**交易幣**。最後一列卻把本幣總額擺在同一欄底下當「合計」，
還用**第一行幣別**的小數位去格式化。

| 單據 | 明細欄合計 | 印出來的「合計」 |
|---|---|---|
| `GS-2609-00012`（USD，匯率 31.7）| **210** | **6,657**（那是新台幣，且無任何幣別標示）|

等於告訴美國客戶他欠 6,657。本國幣單據上兩者相等，所以從來沒有人發現。

**為什麼沒有任何既有檢查會叫**：兩個數字**各自都是對的**（帳上就是這麼記的），
錯的是「把它們放在同一欄」這個版面決定——而版面沒有任何自動檢查。
`AuditJournalBalance`、`INV_ROLLFORWARD`、報表對帳測試全部沉默。

**修法**：合計必須是**上面那一欄的加總**。明細可為不同幣別（模型允許），
故逐幣別各出一列並標明幣別；本幣總額另立一列、標上本位幣代碼、以次要樣式呈現。
六張單據的 `Print` action 一併補 `ViewBag.BaseCurrency`。

**測試**：`Postings/PrintAmountConsistencyTests`（3 支）。斷言方式刻意是
**解析真的產出的 HTML**，不是讀模型欄位——這一格要驗的就是「印出來的紙上，
合計等不等於上面那一欄的加總」。

| 測試 | 釘住什麼 |
|---|---|
| `ForeignCurrencyShipment_PrintedTotal_EqualsThePrintedColumn` | 掛著交易幣別那一列的金額 ＝ 明細欄加總；本幣那一列另計且兩者不相等 |
| `ForeignCurrencyShipment_PrintedTotal_ShowsTheCurrency` | 合計列必須看得到幣別——金額對了但沒有幣別，收到的人照樣按本國幣理解 |
| `ForeignCurrencyReceipt_PrintedTotals_AreLabelledByCurrency` | PUR 三張的版面不同（合計印在表格**外面**的文字裡），同缺陷同修法但回歸無聲，故另釘一支 |

> 突變驗證：把兩種版面的合計都改回 `Model.TotalAmount`，對應的兩支立刻紅。
> 另已確認 `dotnet build` **會編譯 Razor 檢視**（故意寫壞一個 `@foreach` 會出 2 個 error），
> 所以六張檢視改完之後「編得過」本身就是渲染面的守門。

**仍是人工**：版面（欄寬、換頁、logo）只能看輸出。**2026-09-11 業主已抽測確認版面與金額一致性均正常**——這一項至此走完，但它是**抽測不是全量**，六張以外的單據與日後改版都要重看。

### 8.2 簽核設定查不到（5-1 的實測結果）

「缺 contributor 導致核准後靜默停在 PendingApproval」那一半，慣例規則 **R15** 早就在守
（送簽的 DocumentType 必須有**已註冊**的 `IApprovalSyncContributor` 或 Core fallback，零容忍不走 baseline）。
本梯次找到的是**方向相反的另一半**：

> 設定明明存了，卻永遠查不到 → 走「無簽核設定」分支 → **單據直接生效，完全不經簽核**。

前者是卡住（看得出來），後者是放行（看不出來）。後者嚴重得多。

#### 為什麼查不到：兩層疊在一起的雙重不可能

1. `DocumentApprovalConfig` 實作 `IPlantEntity`，設定畫面存檔時
   `ApplyGlobalValues` 把 `PlantId ??= CurrentPlantId` 填上——
   **沒有任何入口建得出「不指定廠別」的設定**；
2. `ApprovalService.GetApprovalConfig` 用的是 `_db.DocumentApprovalConfigs`，
   **沒有** `IgnoreQueryFilters()`，所以全域查詢過濾 `PlantId == CurrentPlantId` 還壓在上面。

於是呼叫端傳 `null` 那條路：條件要 `PlantId == null`，過濾要 `PlantId == 目前廠別`，
**兩個條件互斥**，恆為空。

而 `CLAUDE.md`〈全域主檔規則〉寫的正是「`GetApprovalConfig` 的 PlantId 參數傳 `null`（全域審核設定）」。
實際上七個全域主檔呼叫點裡，Product／Company／Tax 都是傳廠別的（能用），
傳 `null` 的只有兩處——剛好就是壞掉的那兩處。**文件教的寫法是不能用的那個。**

#### 修了一處，另一處卡在 Core 邊界

- ✅ `Modules/PUR/Controllers/VendorEvaluationController.cs`：改傳 `UserContext.PlantId`，
  與其餘全域主檔對齊。查不到的後果不是卡住而是放行——原本會直接把評鑑標成已核准
  **並回寫供應商資格狀態**，完全不經任何人核准且沒有訊號。
- ⏸ `Controllers/CodeEntryController.cs`（兩處）：**Core 檔案**，依 CLAUDE.md 的邊界規則
  必須 Core-first（先在 Core commit 並 push 進 main，部署專案再 `git fetch upstream main`）。
  目前推送被 GitHub 額度擋住，故未動。現況是：**為代碼維護設定簽核流程，存得下去但永不生效**，
  代碼一律直接生效。

#### 順帶：`CLAUDE.md` 那條規則本身要改

〈全域主檔規則〉的「`GetApprovalConfig` 的 PlantId 參數傳 `null`」是錯的，
照著寫就會得到一個永遠不生效的簽核設定。要嘛改成「一律傳 `UserContext.PlantId`」，
要嘛把 `GetApprovalConfig` 改成「先找廠別專屬、再退回全域」**且**加上 `IgnoreQueryFilters()`
並讓設定畫面能建出全域列——後者是比較正統的 ERP 語意，但那是 Core 的設計決定，不是修 bug。
`CLAUDE.md` 也是 Core 檔，同樣卡在同一道邊界。

### 8.3 資料權限與多廠隔離（5-2／5-3 的實測結果）

**沒有抓到缺陷**，三支都是回歸護欄。記在這裡的是「該怎麼測」而不是「修了什麼」。

人工測試很難證明**沒有**看到什麼：測試員只能翻幾頁列表，翻不到不等於查不到。
真正該釘的是兩層互不相干的機制：

1. **全域查詢過濾**（`ApplicationDbContext.OnModelCreating`）。宣告式的，
   `IPlantEntity` 比 `CurrentPlantId`、`IDataAuthEntity` 比角色／組織路徑，
   只要 entity 有實作介面就自動套用——漏的通常不是這一層。
2. **稽核**（`DataAuditService`）。十六支每一支都 `IgnoreQueryFilters()` 之後
   **手寫** `plantId == null || x.PlantId == plantId`。任何一支在 join 進來的第二張表上
   漏掉那個條件，甲廠的稽核就會列出乙廠的單號。這不只是機密外洩——
   關帳前稽核有異常就不准關帳（§8.7），漏一個條件等於「乙廠有爛帳、甲廠關不了帳」，
   而畫面上完全看不出為什麼。

測法是：只在 A 廠建資料，以 **B 廠**身分把十六支稽核全跑一遍，
斷言結果裡不得出現任何 A 廠的單號。一次涵蓋全部，漏哪一支就指名哪一支。

#### 這種「證明沒看到」的測試容易假綠，要先讓它長牙

第一版寫完就綠，但那是**空轉**：B 廠一筆異常都沒有，`foreach` 迴圈根本沒執行，
一支永遠不跑斷言的測試看起來跟真的一模一樣。
補法是先在 A 廠刻意留一筆**可辨識的髒資料**（單號不對應任何單據的孤兒過帳），
並先斷言「A 廠的稽核確實報得出它」，再去斷言 B 廠看不到。
對照組同理：驗「B 廠查不到 A 廠的採購單」之後，必須再用 A 廠的上下文查一次確認查得到，
否則「查不到」可能只是因為資料根本沒建起來。

#### 5-2 那條的真正風險不在權限設定，在欄位有沒有被填

`IDataAuthEntity` 的過濾在沒有組織路徑時退化成 `CreatedByRoleId == CurrentRoleId`，
而 `CreatedByRoleId` 是 `SaveChanges` 時由 `ApplyGlobalValues` 補上的。
只要單據不是經過那條路徑落地——種子腳本、批次匯入、直接 SQL——這個欄位就是 null，
建立者本人一查就是 404，**症狀完全不像權限問題**。
（同一個坑已記在 `feedback-seed-dataauth-createdbyroleid`。）

人工測試只能抽樣幾筆，而抽不到的那些看起來跟成功一模一樣——
現場最後只會發現「這筆報工不見了」，而且無從追。

測試釘的核心是**可重送性**：任何一次中斷之後，沒成功的那些必須還留在 `pending`。
一旦某條路徑誤把未送出的項目標成 `sent` 或 `error`，那筆資料就再也不會被送出去。
涵蓋：`clientId` 去重、priority 排序（機台狀態 1 早於報工 5）、
200／409 視為送出、4xx 標 error 不重試、**401 停止但維持 pending**、
網路例外維持 pending、離線時一筆不送、送到一半斷線只算已送的、
併發 flush 只送一次、`retryFailed`／`clearSent` 的範圍。

#### 兩件執行上的事

- **jsdom 沒有 IndexedDB，環境也裝不了新套件**（無外網）。故自寫 `idb-stub.js`——
  只實作真正用到的 API，並刻意保留「回呼是非同步的」這個真實特性：
  同步觸發會讓「忘了 await」的缺陷在測試裡意外通過。
- **本工作樹沒有 `node_modules`**（`npm install` 在離線環境失敗）。
  跑法是借用主 checkout 的安裝：
  `/home/dev/ProjectZ/node_modules/.bin/jest --rootDir .`
- 測試寫完後做了**突變驗證**：拿掉 `401` 守門與「中途斷線就停」那一行，
  3 支立刻紅——確認斷言不是空轉。

### 8.5 進貨單的目的倉別存不進去（5-5 的實測結果）

`PurchaseService` 建立進貨明細時，`WhCode` / `LocationCode` / `LotNo` **兩條路徑都沒有映射**
（新建走 `CreateGoodsReceiptAsync` 的內聯迴圈、修改走 `CreateGoodsReceiptLinesAsync`，
那段註解自己就寫著有兩份實作）。表單收得到、模型有欄位、編輯畫面也讀得出來——就是存不進去，
於是永遠是 `null`。

#### 為什麼一直沒被發現

桌機的簡化模式過帳看起來完全正常：`GoodsReceiptController` 在 `WhCode`／`LocationCode`
為空時會 **fallback 到產品類別的預設倉儲**。所以只要類別設定有做，貨照樣上得了架。
（這也解釋了 Wave 0 那條人工前置「後沖料的產品類別預設倉儲設定」為什麼是必要的。）

**IQC 放行沒有那道 fallback。**`ReleaseFromQuarantineAsync` 的第二個守門是：

```csharp
if (line == null || string.IsNullOrWhiteSpace(line.WhCode) || string.IsNullOrWhiteSpace(line.LocationCode))
    return;   // 「明細未記錄目的倉別時，不動作」——它自己的註解
```

於是整條進料鏈停在半路，而且**每一步看起來都成功了**：
IQC 登錄回傳 `Pass`、檢驗單建立、抽樣狀態更新——只有貨沒有動。
而應付認列的時機正是「進正常倉」（`AccrueForReceivedQtyAsync`，非免驗品的認列點），
所以連帶 **AP 也永遠不認列**，2152 暫估應付永遠掛著。沒有任何一則訊息會提到這件事。

第二層實害：批號管控品的驗證讀的是 **VM** 的 `LotNo`（會過），存下來的卻是 `null`。

#### 修法

兩條建行路徑各補三個欄位的映射。漏一條的後果不一樣但同樣糟——
只補新建那條的話，**編輯一次進貨單就會把倉別洗掉**。

#### 這條鏈現在被釘住的兩個方向

- **合格**：貨從待驗倉放行到正常倉，應付在**那一刻**才認列，2152 沖平、1155 進項稅入帳、
  每張傳票平衡、§3.2 GR-IR 與滾動平衡稽核皆空。
- **不合格**：什麼都不許發生。貨留在待驗倉、應付一毛不認、連調撥單都不許產生。
  這個方向比合格危險——它是**靜態**的失效，沒有動作也沒有分錄，錯了不會有任何訊號。
  若誤認列了應付，等於承認這批貨要付錢，而它其實正準備退回供應商。

> 順帶記一個測試上的前置：`MobileIqcRecord.InspectorId` 是 NOT NULL 且取自
> `IUserContext.UserId`，所以 **IQC 登錄硬性要求有登入使用者**。
> 從 DI 直接解析服務會拿到沒有身分的實例、寫入當場撞 23502；
> 任何背景排程或整合介面要呼叫它，都得自備一個身分。

### 8.6 報表對帳（5-6 的實測結果）

報表是全站唯一「不經過過帳路徑」的一群查詢，每張各寫各的彙總、沒有共用單點，
所以報表與總帳之間的偏差**不會被任何稽核抓到**——稽核比的是單據與過帳，不是報表與過帳。

#### 資產負債表在畫面上永遠不平（已修，但修的是畫面不是服務）

實測（期初入庫 12,000、出貨成本 4,800、開票收入 12,000＋稅 600、部分收款 5,000）：

| 畫面顯示 | 數字 |
|---|---|
| 資產合計 | 19,800 |
| 負債合計 | 12,600 |
| 權益合計 | **0** |

差額 7,200 正是本期損益（12,000 − 4,800）。

**這不是服務層的 bug。** `BalanceSheetService` 刻意不做期末結轉（損益科目 4~8 不併入權益），
`SmartFactory.MES.Tests/RPT/FinancialStatementTests` 有兩支測試明文守著這個契約，
其中 `BalanceSheetAndProfitLoss_SatisfyAccountingEquation` 斷言的正是
`資產 = 負債 + 權益 + 損益表的 NetProfit`。系統裡沒有任何 3xxx 權益科目、也沒有結轉分錄，
在這個前提下「不假裝有結轉」是正確的決定。

（我一開始把損益淨額直接併進服務層的權益，結果打掉那兩支既有測試才發現這是有意設計，
已回退。記著：報表語意的改動要先看有沒有測試在守。）

問題出在**畫面**：只擺三張合計卡，看報表的人得到的是一組湊不起來、又看不出少了什麼的數字。
已由控制器補上第四個數（`IProfitLossService` 從最早期間累計到 asOfPeriod 的 `NetProfit`），
畫面改成四張卡加一行恆等式檢核，差額不為 0 時亮警示。

#### 對得起來的（列為回歸護欄）

- **應收帳齡**：分桶合計 == 各桶相加 == `GetOutstandingBalanceAsync` == 總帳 1170 應收帳款。
  部分收款只掛未收的那一段（`AmountLocal − ReceivedAmount × ExchangeRate`），
  與 AP 帳齡用的是同一條公式，兩邊一致。
- **損益表**：4xxx／5xxx 逐科目與總帳淨額相符，符號慣例（收入貸方為正、費用借方為正）沒寫反。
- **資產負債表逐科目**：1／2 開頭且有餘額的科目一個都沒漏。

#### 未納入自動化

- ~~**庫存餘額表**~~ **2026-08-30 已補**。原本的理由（是 `Inventories` 的直接投影、

### 8.7 月結狀態機的死結（5-7 的實測結果）

`MonthEndService` 的步驟 8「封鎖庫存異動」會呼叫 `StartClosingAsync`，把期間推進
`PeriodStatus.Closing`。`Closing` 擋掉所有一般過帳
（`JournalEntryService` 只放行 `JournalEntryType.Adjustment` 的手工調整分錄，
`InventoryPostingService` 的七道閘門則是全擋）。於是：

```
關帳要稽核過 → 稽核異常多半得靠過帳去修（補開票、補認列、沖銷、調整庫存）
            → 過帳被 Closing 擋 → 期間永遠停在 Closing
```

而 `IAccountingPeriodService` 原本沒有任何回頭路：
`StartClosingAsync` 只收 Open/Reopened、`ReopenPeriodAsync` 只收 Closed，
**Closing 不是任何一個轉換的來源狀態**。唯一的出路是直接改資料庫。
這個情境一點都不罕見——步驟 8 打勾之後才跑到步驟 10 才發現稽核不過，就中了。

已補 `CancelClosingAsync`（服務層 + `/MonthEnd/CancelClosing` + 清單畫面上步驟 8 的「取消月結」按鈕）：
- 只收 `Closing`：尚未開始的沒東西可取消，已關帳的要走重開帳（那是需要核准的動作），
  否則這個入口就成了繞過重開帳的後門。
- 曾關過帳的期間退回 `Reopened` 而不是 `Open`——「這個期間關過帳」是稽核軌跡。
- 同時把清單的步驟 8 退回未完成，否則畫面顯示「已封鎖」而期間其實沒鎖。
  步驟 9（期末調整分錄）刻意不動：已經開出去的分錄是既成事實。

### 8.8 期末費率重估在正常操作路徑下不會發生（5-8 的實測結果）

兩件事疊在一起，結果是**這一項用畫面根本執行不了**。

#### 一、月結步驟 4 有兩個互相衝突的動作，而順序是致命的

| 動作 | 呼叫的服務 | 做什麼 |
|---|---|---|
| 清單上按「完成」 | `WorkOrderCostFinalizationService.FinalizeAsync` | 只把 `Preliminary` 翻成 `Final`，**不重估、不產生任何分錄** |
| `/MonthEnd/RunActualRateReestimation` | `ActualRateReestimationService.RunAsync` | 依實際費率回刷成本並產生調整分錄 |

兩者的註解都自稱是「步驟 4」。而 `RunAsync` 原本只撈 `Status == Preliminary`——
先按完成就等於把該期成本全部鎖死，之後再跑重估**一筆都撈不到，回傳 0 筆、
不產生分錄、完全沒有訊號**。工單成本從此停在標準費率算出來的值，實際費率的差額永不入帳。

#### 二、而且步驟 4 根本沒有執行重估的按鈕

`MonthEndController.RunActualRateReestimation` 存在、`IActualRateReestimationService` 也注入了，
但**沒有任何一支 View 呼叫它**（`isBatchStep` 只認步驟 6 匯率重評與步驟 7 NRV）。
操作員在畫面上能按的只有「完成」——也就是那個會把成本鎖死的動作。
所以「先鎖定再重估」不是使用者可能弄錯，而是正常操作路徑的**唯一**走法。

#### 修法

1. `RunAsync` 不再篩 `Status`，改以「本期的成本記錄」為範圍。**這是冪等的**：
   差額取「新值 − 現值」，已重估過的記錄第二次算出來就是 0，不會重複回刷也不會重複產生分錄。
   （新增 `Reestimation_RunTwice_ProducesNoSecondAdjustment` 釘住這件事——
   放寬篩選條件之後，冪等才真正需要被守。原本那支「第二次跑不會重複」是因為撈不到，
   綠得毫無意義。）
2. 月結畫面步驟 4 補上「執行批次」按鈕與部門實際費用輸入 Modal
   （比照步驟 6 匯率那個的既有樣式，每行「工作中心:實際人工:實際製費」）。
   沒有這份資料就算不出實際費率——它是分子。

> 判定是「反引號配對區間內含 CJK」，所以在既有 template literal 附近加一段中文註解，
> 會讓配對位移而報在一段看起來毫不相干的字串上。說明要寫在 `<script>` 之外。

### 13.8 借入／客供／樣品的分錄落點（2026-09-22）

**起因**：查 §13.7 時順帶發現 `BuildJournalLines` 的科目只按 `(direction, typeCategory)` 決定，
而 `Loan`／`Sample` 兩個類別**沒有自己的分支**——六個異動類別（`IB`／`BR`／`IL`／`LR`／`CI`／`CR`）
全部落到 fallback：入庫一律貸 2152「進貨暫估應付」、出庫一律借 5210「報廢損失」。
業主確認業務語意後修正。

**業主給的語意**（2026-09-22）：
- **借入**：向外部借來的，沖銷走「借入還回」，但**成本仍須依借入成本計算**
- **客供**：客戶提供自己的料做該客戶訂單之用，可能退回，**不算我們的財產或成本**

**兩者會計性質相反**，而原本走同一條 fallback，所以不可能兩個都對——實際上都錯。

| 類別 | 原本落點 | 正確落點 | 為什麼 |
|---|---|---|---|
| `IB` 借入（+1）| 貸 2152 進貨暫估應付 | 借 1401／**貸 2170 其他應付款—借入物料** | 2152 由採購鏈的 AP 認列來沖，借料沒有發票會來 → 長出一筆 AP 端不知道、永遠沒人沖的負債，且 `GRIR_AGING` 天天報假異常（與 4210 存貨盤盈那條註解同一個道理）|
| `BR` 借入還回（−1）| 借 5210 報廢損失 | **借 2170**／貸 1401 | 🚨 還料給人家記成報廢：憑空多一筆費用，而 2170 那筆負債永遠留著 |
| `IL` 借出（−1）| 借 5210 報廢損失 | **零分錄** | 我們的料換了地點，所有權沒移轉。原本「料借出去就認損失」，還回來（`LR`）又貸一次存貨，兩趟下來存貨少一份、費用多一筆 |

| `CI` 客供進貨（+1）| 貸 2152 | **零分錄** | 客戶財產，進存貨科目等於同時虛增資產與負債；我們只就加工費開發票 |

**起因**：§13.8 收尾後業主問「除了用料號區分，是否可將客供料排除不計入成本，
因為那不屬於公司的資產」。查證後**業主是對的，而我原本的建議是繞路**。

**為什麼一定要有隔離維度**：移動平均的成本池是 **(PlantId, ProductCode)**
——`UpdateMovingAverageCostAsync` 的分母取該品號**全廠**在手量，
再把新均價寫回該品號**所有** Inventory 列（該方法註解自己寫著「均價是全廠的，不是儲位的」）：

```
自有 100 @10，客供 100 @0，再進自有 100 @20
  正解 (100×10 + 100×20) / 200 = 15
  實際 (200×10 + 100×20) / 300 = 13.33   ← 分母含了客戶的料
```

而 13.33 是個看起來完全正常的單價，會讓之後每一張出貨的毛利莫名偏高。

**原建議（另開品號）錯在哪**：它確實可行——換品號之後分母自然分開。但它要求使用者
為同一個物料維護兩套品號、兩套 BOM 對應、兩套安全庫存，而**客供與自有本來就是同一個物料，
只是所有權不同**。正解是把「所有權」做成維度，而系統已經有現成的維度：倉別。

**交付**：新增 `WarehouseType.CustomerSupplied`（enum 以 int 序數持久化，
加在**最後**故不需 migration；插在中間會讓既有倉庫類型整批位移而每一筆都還是合法值）。

| 改動 | 內容 |
|---|---|
| 均價**分母**排除客供倉 | 客戶的料不進我們的成本池 |
| 均價**寫回**排除客供倉 | 否則自有料的均價會寫到客供料上，客戶的料於是「有了成本」 |
| 回沖（作廢）同樣兩邊排除 | 與更新同一個口徑；客供料入庫本來就沒進過均價，沒有均價可沖 |
| 過帳時客供倉一律 `UnitCost = 0`，**MA 與 FIFO 兩條都跳過** | FIFO 那條特別需要：客供入庫沒有單價可帶，而沒帶單價的入庫會被 FIFO 守門丟例外——「客供料＋FIFO 品號」這個完全正常的組合原本**根本過不了帳**，而錯誤訊息講的是成本層，跟客供料八竿子打不著 |
| 過帳守門 ③-b：`CI`／`CR` 必須落在客供倉 | 放過帳服務不放畫面——桌機、手機 PWA、倉儲 API 都走它，畫面層繞得過 |

**兩個刻意的設計決定**：

1. **只擋一個方向**。守門只管「客供料進來時必須落在不計價的倉」，反向不擋——
   客供料本來就要能被領去生產（`IO` 從客供倉出庫）、調撥、退回。
   寫成「非 `CI`／`CR` 不得動客供倉」會讓客供料領不出來，而那正是它存在的用途。
2. **`Inventory.UnitCost` 恆為 0**，所以六處存貨金額報表（評價／週轉／帳齡／呆滯／
   儀表板／價值表）**不必逐一加排除條件**——它們都是 `QtyOnHand × UnitCost`。
   這是選「成本歸零」而不是「報表各自過濾」的理由：後者要改六個地方，
   而且下一個新報表會忘記。

> **與 `Quarantine` 的差別**：待驗倉排除的是**可用量**（IQC 沒放行不准動），
> 客供倉排除的是**計價**（料可以正常領用，只是價值不進我們的存貨）。
> 所以 `GetAvailableQtyAsync`（儲位級）**不**排除客供倉。**數量要管、成本不算。**

#### 2026-09-24 複評：結論不變，但當時只看了一條軸

業主要求「先不管之前的作法」重評一次「客供料是否用另一個料號管控較佳」。**維持倉別**，
但 9/22 的論證有一個缺口要補上：**它整段只在談成本，沒有談可用量**。

**先訂正一句話**：程式註解裡寫的「分品號、分批號都不管用」是寫過頭了。
分批號成立（批號不在成本池的鍵裡），**分品號不成立**——鍵 `(PlantId, ProductCode)`
本來就含品號。§13.9 原文其實寫對了（「換品號確實可行但那是繞路」），
是 `IDataAuditService` 與 `CustomerSuppliedLocationAuditTests` 的轉述講死了。已一併訂正。

**換品號在第二條軸上一樣解不開**。`GetPlantAvailableQtyAsync` 只排除待驗倉，
客供料計入廠級可用量：

```
甲客戶供 100、乙客戶供 50  →  客供品號 ABC-CS 的廠級可用量 = 150
MRP 為乙的工單淨算時，照樣把甲的 100 抵掉
```

單一「客供品號」只是把同一個分母問題換個名字。要真的解開得**一個客戶一個品號**，
而那才是代價的來源：`Product` 是全域主檔（筆數＝物料數 × 客戶數），更致命的是
**全庫沒有任何替代料機制**（`Substitute|Alternate` 在 `Modules/` 零命中），
所以甲的工單要領 `ABC-CS-甲` 就得有一張指定它的 BOM——BOM 是最不該分叉的主檔。

而「一客戶一品號」換到的東西**倉別也給得起**：`WarehouseType.CustomerSupplied`
可以開多個倉（`CS-甲`／`CS-乙`），成本隔離是**類型驅動**所以照舊，歸屬靠倉別分，
品號一個、BOM 一張。**故新增規定：客供倉一客戶一個。**

**真正還沒解決的是 MRP 口徑，而它不是一個開關**：

| 口徑 | 後果 |
|---|---|
| 含客供料（現況） | 甲的料抵掉乙的需求，**誤配** |
| 排除客供料 | MRP 為甲的工單去買甲已經給過我們的料，**重複採購** |

兩個方向都錯。要對，需求端得知道「這張工單用的是哪個客戶的客供料」，而那條線不存在：
客供料走 `SampleDoc`（`EntityCode` 記了客戶），過帳進 `Inventory` 之後客戶就掉了
（`Inventory` 只有 `LocationCode` 與 `LotNo`，沒有所有權欄位），工單也沒有欄位接得回去。

**相稱的處置**（現行資料 0 筆客供單）：不蓋分客戶淨算那套機器，量還不存在。
但把現況從**沉默的繼承**變成**明示的決定**——`GetPlantAvailableQtyAsync` 含客供料
不是有人決定的，是沒人問過。已補 `CustomerSuppliedStockCountsAsAvailableTests` 3 支
（客供計入／待驗不計入／兩個客供客戶在加總裡分不開）釘住現況，突變驗證：
把客供倉也排掉 → 紅 2 支、待驗那支不動。**觸發條件寫在測試與方法文件裡：
第二個客供客戶出現的那一天，前提就破了，必須回來補歸屬。**

**稽核判準一併改寫**：`CUSTOMER_SUPPLIED_MIXED_PRODUCT`（共用品號）→
`CUSTOMER_SUPPLIED_WRONG_LOCATION`（客供異動落在非客供倉）。
舊判準在新方案下是**錯的建議**——品號共用不再是缺陷。
與過帳守門的分工：守門擋未來，稽核找過去（守門上線前已落在一般倉的遺留資料，處置是調倉）。

**已掛進 `RunAllAsync`**（＝沒調倉就不准關帳）。原本按 `AuditOrphanPostingAsync` 的前例
打算唯讀盤查先行，業主當日確認**現行資料沒有客供單（有也只是測試資料）**，
所以那個風險（既有部署被擋在月結當天）不存在，直接掛入。
另補一支 `Audit_IsWiredIntoRunAll_AndBlocksPeriodClose` 釘住掛載本身——
**寫好一支稽核卻忘了註冊，它就只是一個沒有人呼叫的方法**，全綠、零訊號，
與 §13.8 記的「有讀取點但結果被丟掉＝沒有讀取點」是同一種形狀。

**測試與變異驗證**：

| 變異 | 紅的支數 |
|---|---|
| 均價分母不排除客供倉（還原稀釋） | 1 |
| 拿掉過帳層的計價跳過 | 1（FIFO 那支）|

這是唯一剩下的一步——稽核已經在擋關帳了，沒有客供倉就開不出客供單（過帳守門 ③-b 會擋）。

### 15.2b 🔴 W1-F8：分批上架的**中間發生退貨**，暫估沖不掉、等額變成假性價差（**已修**）

起因是這兩支 PR 各自修了 `AccrueForReceivedQtyAsync` 的不同一半

實測（收 10、上架 6 並認列、退 2、再上架 4 並認列，收貨單價＝採購單價，真實價差 0）：

```

`(ArDocType || ArReturnDocType)`**——AP 這裡是全庫唯一漏掉的一個，

**變異驗證**：拿掉 `|| ApReturnDocType` 該支立刻紅回 `-200 / +200`。

### 15.2c 🔴 合併後 `main` CI 紅：單位小數位快取讓 12.5 被捨成 13（測試地基，**已修**）

#131／#132 合併進 `main` 後那一輪 CI 紅了，失敗的是 §15.2 那支
`BatchedPutAway_DoesNotBookPhantomVarianceOnIntermediateBatches`：

```

**根因**：`UomService.GetDecimalPlacesAsync` 對**查不到的單位一律回 0 位小數**，
而小數位有一份 10 分鐘的行程級快取。乾淨的庫一開始沒有 `PC`，某支較早的測試

**但不像 `UomController` 那樣順手清快取**。於是 `RoundQtyAsync("PC", 12.5)` 走 dp=0 →
`Math.Round(12.5, 0, AwayFromZero)` = **13** → 撞上採購單超收守門。

全套 476 支裡**只有這一支帶小數量**，其餘都是整數，捨了也看不出來——所以它是唯一會現形的。
**生產程式不受影響**：`UomController` 的建立／修改／刪除三處都有 `InvalidateDecimalPlacesCache()`。

**修正**：`FlowTestBase.ResetAsync` 建完主檔後清一次該快取。
變異驗證：拿掉那一行，真全新庫立刻紅回同一則訊息。

#### 為什麼「本機全綠」對這一類缺陷沒有證據力

`PC` 早就躺在共用測試庫 `SmartFactoryMES_Test` 裡（跑過幾百輪），所以本機任何時候
載入快取都查得到它。**同一份程式碼，差別只在那個庫有沒有被跑過。**

⚠️ 追查時還踩到一個更麻煩的陷阱：`TestWebApplicationFactory.Dispose` 會把
`ConnectionStrings__DefaultConnection` **設成 null**——即使那個值不是它設的。
兩個 collection 各建一個 factory，第一個 dispose 之後環境變數就沒了，
第二個建構子看到空值就退回寫死的 `SmartFactoryMES_Test`。
於是「用環境變數指到另一個庫」只對前半段生效，**後半段靜靜跑回舊庫**，
而測試全綠、毫無訊號（判斷依據：新庫裡 `FLOW-*` 產品 0 筆、舊庫 53 筆）。
本次是改 `FallbackTestConnection` 常數才真的連到新庫、才重現得出來。
CI 之所以沒被這個問題咬到，純粹是因為它指定的庫名和 fallback 剛好同名。

**要在乾淨庫上驗證時**：改 fallback 常數，不要只設環境變數。

### 15.7 順帶記下的兩件事（**2026-09-11 已查證並收口，不必留到 Wave 3**）

> **兩件都成立，而且第一件比原記述更嚴重。** 原本寫「各有 3 個 `step="1"` 的數量欄位」，
> 實際是**各 4 個**（第 4 個在「從出貨單／採購單挑明細」的對話框裡，原記述沒掃到）。
> 查證方式與結論如下，修正已隨本批提交。

**① 兩支 `_Form.cshtml` 確實沒有呼叫 `applyUomStep`——而且是半套，不是沒做**

`SalesReturn`／`GoodsShipment` 兩支**早就**把 `uomDecimals` 注入 `window.uomDecimals`
（各自 script 區塊第一行），也在單位換算時讀它——**只是從來沒有套到數量輸入欄位上**。
更明確的證據是兩支的 `onUomChange` 裡各留著一句註解：

```js
function onUomChange(e, sel) { /* return qty step fixed at 1 */ syncStockQty(sel.closest('tr')); }
```

`git log -S` 追到兩句註解同源於 `f8ce7470`（2026-05-16「強化資安及增加銷售管理模組」），
而**同一個 commit 裡的 `SalesOrder/_Form.cshtml` 有 2 處 `applyUomStep`**。
也就是說三支是一起寫的，抄漏了兩支，還留下一句把它寫成刻意決定的註解。

**為什麼這是真缺陷而不是設計選擇**：`SalesReturnLine.ReturnQty` 與 `GoodsShipmentLine.ShipQty`
都是 `decimal`，而且兩支的 Controller **都呼叫 `RoundQtyAsync`**（依單位精度捨入）——
伺服端按單位精度收數量，畫面卻只收整數，**兩邊契約相反**。
症狀：小數單位的品號（例如 KG）出不了 6.25，退不了 6.25，而瀏覽器原生驗證的訊息
只會說「請輸入有效值」，不會指向真正的原因。訂單那一端可以下 12.5 KG，
於是**訂單永遠出不完**。

修正（共 7 支 View）：
- **`SalesReturn`／`GoodsShipment` 各 4 處**：伺服端算繪列改 `UomStepHelper.GetStep/GetMinPositive`；
  `addLine` 與「由來源單帶入」兩個 JS 模板改 `step="any" min="0"` 並在建列後呼叫 `applyUomStepAsync`；
  挑選對話框的數量輸入改 `step="any"`；`onUomChange` 補回 `applyUomStep`（那句註解一併刪掉）。
- **同型缺陷一併收口**：`GoodsReceipt`／`GoodsReturn` 的挑選對話框也是 `step="1"`（收貨／退貨量同樣輸不進小數）。
- **模板初始值**（`SalesOrder`／`PurchaseRequest`／`CrossPlantTransfer`／`GoodsReceipt`／`GoodsReturn`）：
  原本靠「選了產品或單位才被 `applyUomStep` 修正」，先輸數量再選產品那條路徑會被 `min="1"` 擋住。
  五支都有修正路徑（已逐一確認），故初始值放開為 `step="any" min="0"` 是安全的。

**② R9 守門對 `step="1"` 是盲的——已補 R9(c)**

原記述正確。R9 (b) 只掃 `step="0.\d+"`，而 `step="0.x"` 只是 spinner 不好按，
`step="1"`／`min="1"` 才是**讓小數根本輸不進去**的那一個——規則對更嚴重的違反視而不見。

已新增 **R9(c)**：數量欄位（class 帶 `line-qty`，或 `name` 以 `Qty` 結尾，排除 `readonly`）
不得寫死 `step="1"`／`min="1"`；例外記入 `baseline-R9c.txt`，目前只有一筆
（`InspectionOrder/_Details` 的抽樣數與不良數——計件且與 UOM 無關）。

**突變驗證做了三次，第二次抓到我自己的錯**：

| 突變 | 結果 |
|---|---|
| 把 `SalesReturn` 的 Razor 列改回 `step="1" min="1"` | ✅ 紅，且指名到該檔 |
| 把 class 判準改名（模擬欄位改名） | 🔴 **第一版沒紅** |
| 把 `name` 判準改名 | （同上修正後）✅ 紅 |

第一版的自我檢查寫成 `probed >= 40`，而 `line-qty` 與 `name$=Qty` 兩個判準**各自命中 42、聯集 47**——
任一邊失效，另一邊都會把它掩護到 40 以上，規則於是靜默全綠。
改成**逐判準各自檢查**（各 `>= 35`）後兩個突變都紅得精準。
**這正是 R21／R22／R32 立下 `probed > 0` 自我檢查要防的形狀，而我第一次仍然寫錯了**：
自我檢查的門檻必須對著「每一個會獨立失效的判準」，不是對著聯集。
