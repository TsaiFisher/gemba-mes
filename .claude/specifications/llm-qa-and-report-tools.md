> **Phase 3 交付紀錄（2026-08-24）——三件落地時才看得到的事：**
>
> 1. **工具參數與畫面查詢列是兩套詞彙，而且不會統一。** 工具那一側是查詢語意
>    （`customerCode`／`idleDaysThreshold`／`keyword`），常用查詢存的是目標畫面的網址參數
>    （`searchCustomer`／`idleDays`／`searchProduct`）——後者還受六張已上線報表的網址約束。
>    → 新增 `ReportScreenBinding.ParamMap`（工具參數名 → 畫面欄位名），
>    與 `FilterKeys` 白名單放在一起；`ToolParamsToSavedQueryTests` 有一支釘住
>    「ParamMap 的每個目標都必須在 FilterKeys 內」——漏一筆的症狀是那個條件**永遠存不進去**，
>    而查詢照樣存得起來、照樣點得開。
>
> 2. **🚨 對不上的參數一定要回報，不能靜默丟。** 畫面查詢列表達不了的條件（例如 `topN`）
>    本來就帶不過去，這無可避免；但不講的話，使用者會以為那張常用查詢等於他剛才問的那一題，
>    **而它其實範圍更寬**——下次點開數字比當初大，且沒有任何跡象。
>    → 存檔成功訊息會列出被丟掉的參數名。
>
> 3. **憑據是 `turnId`，不是畫面送回來的工具鍵與參數**，而且只認 `Answered`／`SummarySkipped`
>    那兩種結局的輪次。收下客戶端給的參數等於讓「另存」變成一個**可以憑空寫入任意查詢定義**的入口，
>    而那張定義日後可能被掛上排程、定期寄出。這同時滿足 §9.2-3
>    「尤其是要另存為排程報表之前」必須先確認過——存得起來的東西必定已經真的跑出過結果。
>
> **刻意不做「直接另存為排程」**：排程還要頻率、收件人、輸出語系，自然語言裡沒有這些。
> §7.9〈對後續階段的加成〉給的路徑就是「先存常用查詢 → 用順了 → 加排程」。

### 17.1 版控邊界：放哪個 repo、什麼進 git

#### 放 ProjectZ，不放 Core

| 判斷 | 理由 |
|---|---|
| **一律實作為 ProjectZ 的 `Modules/` 顧問模組** | Core 是零衝突骨架；本功能是業務層能力。且 `Program.cs:270-275` 已用**組件掃描自動載入 `IAppModule`**，新增模組**零 Core 改動**——不觸發 `check-core-drift.sh`、不需要 upstream-first、不影響 `update-core.sh` merge |
| 只有真的要動 Core 檔案時才走 upstream-first | 目前預期為零（§15.5 已盤點）。若 Phase 2 需要 Core 的權限或選單擴充點，依 `CLAUDE.md`〈邊界 hook 與 Core 修正的提交順序〉：Core commit+push → ProjectZ `git fetch upstream main` → 才提交 |

**建議模組代號**（沿用既有三碼慣例 ACT/BAS/FIN/INV/MFG/ORD/PUR/QCR/RPT）：

- `Modules/RPS`（Report Scheduling）— Phase 0：`IReportTool`、`ReportToolCatalog`、`ReportDefinition`、派工器、S-1～S-5
- `Modules/QAA`（QA Assistant）— Phase 1/2：RAG、Ollama 用戶端、S-7

> 而 RPS 是**跨模組的基礎設施**（它排程的報表來自 ORD/INV/PUR/MFG/FIN 各處）。
> 混在一起之後，「關掉排程」與「關掉毛利報表」會變成同一個開關。

**一個開關對一個模組**，是這個切分最實際的好處：`RPSModule.RegisterServices` 開頭即


**為什麼兩支都預設關**：

- 最低驚訝原則——公開發布後 `git clone` + 照現行流程部署，**行為必須與今天完全相同**。
- `ReportTools` 開啟會多一支每分鐘輪詢的 hosted service 與一個必填的儲存路徑；不用排程的部署不該被迫承擔。
- 兩支分開，是因為 **Phase 0 零 LLM 依賴**：只想要「例行報表自動產生」的客戶不該被要求裝 GPU。

**三條實作規則**：

1. **依賴要顯式檢查並出聲**：`QaAssistant=true` 而 `ReportTools=false` 時，Phase 2 的工具目錄會是空的——
   啟動時必須 `LogWarning` 明講，**不得靜默**（同 §7.8 S2：靜默停止與靜默續行一樣糟）。
2. **`ReportTools=true` 而 `Reports:StoragePath` 為空 → 啟動即失敗（fail fast）**，
   不要等到第一次排程執行才在背景服務裡炸掉——那時只有 log 檔看得到。
3. **開關只在啟動時讀一次**（`RegisterServices` 階段），**不支援熱切換**。要寫進部署文件，
   否則有人改了 `appsettings.json` 沒重啟，會以為功能壞了。

### 17.3 資料庫：Phase 0 併主 context，Phase 1 必須拆 `QaDbContext`

#### 更正 §三 的原假設

原文寫「pgvector 相關表拆獨立 migration bundle，只在功能開啟時觸發」。**現行架構下做不到**：

```csharp
// Program.cs:476-481
if (builder.Configuration.GetValue("Database:AutoMigrate", true))
{
    using var scope = app.Services.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<ApplicationDbContext>();
    db.Database.Migrate();        // ← 套用該 context 的「全部」pending migration，不看任何 Features 開關
}
```

EF 的 migration 粒度是 **DbContext**，不是 bundle；同一個 context 裡沒有「這幾筆先不要套」這種東西。
後果不是「QA 功能沒裝好」，而是——若把 `HasPostgresExtension("vector")` 放進主 context，
**每一個部署的 `Migrate()` 都會執行 `CREATE EXTENSION vector`，PG 未安裝 pgvector 的環境會在啟動時直接失敗，整個系統開不起來**。
那正是把選用功能變成硬相依的典型方式。

#### 正解：兩張表分兩邊放

| 資料 | 去處 | 理由 |
|---|---|---|
| `ReportDefinition`／`ReportRun`／`ReportRecipient`（Phase 0） | **主 `ApplicationDbContext`**，以 `Data/ApplicationDbContextExtensions.cs` 的 partial 加入（符合 `CLAUDE.md`「不得修改 `ApplicationDbContext.cs`」） | 零特殊相依。表永遠建立，功能關閉只是沒人寫入——**空表無害，換來的是切換開關不必跑 migration** |
| 手冊向量表（`DocChunk`，Phase 1） | **獨立 `QaDbContext`**，`MigrationsHistoryTable("__EFMigrationsHistory_Qa")`，只在 `Features:QaAssistant:Enabled` 時才 `Migrate()` | 選用功能的表不該在每個部署都建；且 `DocChunk` 隨手冊重建大量寫入／刪除，生命週期與業務資料完全不同 |

> **2026-08-05 更正**：本節原本的核心理由是「`CREATE EXTENSION vector` 會讓沒裝 pgvector 的部署啟動即失敗」。
> §10.6 定案 Phase 1 不引入 pgvector（`embedding` 存 `real[]`、記憶體精確檢索），該風險已不存在。
> **拆 `QaDbContext` 的結論不變**，理由改為上表所述。

`QaDbContext` 的連線字串預設沿用主連線（同一個資料庫、不同 migration 歷史表），
必要時可由 `Features:QaAssistant:ConnectionString` 指向另一台——這對「把向量索引放到有 GPU 的機器」很有用。

**兩個連帶事項**：

- `scripts/check-snapshot-drift.sh` 目前只看主 context 的 snapshot。新增第二個 context 後，
  該腳本要嘛顯式 `--context ApplicationDbContext`，要嘛一併納入 `QaDbContext`——
  **不處理的話，`dotnet ef migrations add` 會在兩個 context 之間挑錯對象**，而錯誤訊息不會直說。
- 關閉功能**不刪表、不 drop extension**。要徹底移除的客戶，文件寫明手動 SQL；
  不提供自動 drop（`ReportRun` 是 §8.6(c) 的稽核資料，誤刪不可回復）。

### 17.4 選單與權限：開燈那一刻會發生授權擴散

這是本章最容易踩、也最難事後補救的一項。

`RolePermissionSeeder` 的步驟 3b（[`ComputeBackfill`](../../Services/RolePermissionSeeder.cs#L265)）會在**每次啟動**時，
把「全系統從未出現過的選單鍵」自動補給各授權角色，補給誰由 [`GroupToModule`](../../Services/RolePermissionSeeder.cs#L45)
＋ [`Matrix`](../../Services/RolePermissionSeeder.cs#L102) 決定。

於是有兩個對稱的失敗：

| 情境 | 後果 |
|---|---|
| 新群組**沒**登錄 `GroupToModule` | 落入 `_UNKNOWN` → default-deny → **畫面做完了但沒有任何人看得到**（§16.2-1） |
| 新群組**照抄 RPT 那一列** `(F,R,R,R,R,R,R)` | 開關一打開，**OP 作業員立刻拿到報表排程與 LLM 助理的 Read 權限**——而且是自動補的，沒有人按過任何按鈕 |

因為開關關閉時選單不登錄、鍵「從未出現過」，所以**補鍵發生在第一次開燈的那一次啟動**。
→ **矩陣必須在開燈之前就是對的**；補完之後再改矩陣**不會回收**已發出的授權（既有鍵不重賦是刻意設計）。

**建議的群組切分**（關鍵在於「個人工具」與「管理功能」不是同一件事）：

| 群組 | 畫面 | 建議矩陣（HQ, SALES, WH, PROC, FIN, MGR, OP） | 理由 |
|---|---|---|---|
| `REPORT_SELF` | S-2 我的常用查詢、S-3 報表收件匣 | `(F, F, F, F, F, F, F)` | 這是**個人工具**，存的是自己的查詢參數；執行時檢查的是**目標報表**的 MenuKey（§7.9-4、§16.2 權限動詞說明），所以全開不構成越權 |
| `REPORT_ADMIN` | S-1 排程維護（看全部排程）、S-4 執行紀錄 | `(F, N, N, N, R, R, N)` | 看得到別人的排程與收件人＝看得到「誰在定期收哪些機密報表」，屬管理視角 |
| `QA_ASSISTANT` | S-7 對話畫面 | 第一版建議 `(F, N, N, N, N, R, N)` | §八 的機密邊界（待決 #2）裁決前不宜擴大；Phase 2 依裁決結果再放寬 |

> 這張表本身也是**待決 #2 的下游**：報表機密等級裁決完，`QA_ASSISTANT` 的矩陣才有依據。
> 在那之前先給最小集合，日後放寬容易、收回困難。

### 17.5 pgvector 與 Ollama：一律原生安裝，**不走 Docker**（2026-08-05 定案）

> **2026-08-05 再更正（§10.6）：Phase 1 不裝 pgvector。**
> 實測本機 `pg_available_extensions` 無 `vector`，而語料只有 134 頁 × 2 語系（估 300–800 chunks、約 3.3 MB 向量），
> 精確餘弦檢索 < 1 ms，ANN 索引買不到東西。→ **下表 pgvector 那一列與文末「已知落差」整段延後至 P3 之後**，
> 若真的需要再依 `IDocVectorStore` 換實作。本節其餘關於 **Ollama** 的內容（原生安裝、埠綁定、不用 Docker 的四個理由）**全部不變**。

> **本節取代原「Docker override 檔」規劃。** 原方案要維護 `docker-compose.qa.yml`
> （`db` 換 `pgvector/pgvector:pg16` ＋ 加一個 `ollama` service ＋ 模型落 volume）。
> 移除理由見下方「為什麼不用 Docker」。

#### 兩個外部相依，各自獨立安裝

| 相依 | 安裝方式 | 磁碟 |
|---|---|---|
| **pgvector** | 對現有 PostgreSQL 16 直接裝擴充：`sudo apt install postgresql-16-pgvector`。`CREATE EXTENSION vector` 由 `QaDbContext` 的第一個 migration 執行 | **1–2 MB**（＋索引 <100 MB） |
| **Ollama** | 原生安裝於**執行推論的那台機器**（Linux 伺服器用官方 script＋systemd；開發機見 §17.11 走 Windows 端） | 執行環境 1–1.5 GB ＋ 模型（§四） |

`Features:QaAssistant:OllamaUrl` 指向該服務即可——**Ollama 是進程外、走 HTTP 的**，
與應用程式的部署方式（原生／容器／不同主機）完全解耦。這也是本節能夠移除 Docker 的根本原因。

#### 為什麼不用 Docker

| # | 理由 |
|---|---|
| 1 | **開發機根本沒有 Docker**（實測：`docker` 指令不存在，PostgreSQL 是 apt 版 16.14）。原規劃等於要求開發者為了驗證這個功能先裝一整套 Docker，而驗證的東西（HTTP 呼叫 Ollama）根本不需要容器 |
| 2 | **模型放進 volume 就等於放進 WSL 的 vhdx**。vhdx 只增不減，模型刪掉空間也不會還給主機（§17.11）。原生安裝可以把模型放在任何一顆磁碟，`ollama rm` 即時回收 |
| 3 | **`db` 換 image 是有風險的動作**。原方案要把既有 `postgres:16-alpine` 換成 `pgvector/pgvector:pg16` 才能用 pgvector；裝擴充只是 `apt install` ＋ 一句 `CREATE EXTENSION`，**完全不動既有資料庫服務** |
| 4 | GPU 直通在容器裡要顯式宣告（`deploy.resources.reservations.devices` ＋ NVIDIA runtime），**漏宣告會靜默跑 CPU、沒有任何錯誤訊息**，只是回應從數秒變數十秒。原生安裝沒有這一層 |

#### 為什麼是 Ollama 而不是 LM Studio（2026-08-05 評估後維持原案）

開發機上 LM Studio **已安裝**，且它有一項 Ollama 沒有的能力：內含 llama.cpp 的 **Vulkan 後端，
能用 Intel UHD 770 內顯**（Ollama 的後端只有 CUDA／ROCm／Metal，本機內顯完全用不上）。
即使如此仍維持 Ollama：

| | Ollama | LM Studio |
|---|---|---|
| 授權 | **MIT** | **閉源專有**。可免費使用（含工作用途），但不是開源授權、**不可隨產品散布** |
| 部署形態 | Linux systemd 服務、官方安裝腳本、無 GUI | 桌面 GUI 為主；`lms` CLI／headless 為輔，Linux 走 AppImage |
| 資源占用 | 較輕 | 較重（開發機實測判斷） |
| 對 §17.11.6「採用者承諾」的影響 | 選用而已 | 等於要求客戶在 **ERP 伺服器**上裝一套專有 GUI 應用 |

決定性的是前兩項：**把桌面應用當 daemon 跑在客戶的 Linux 伺服器上，是「開發機很順、上線很痛」的選擇。**

#### 連帶決定：client 走 Ollama **原生 API**，不走 OpenAI 相容層

Ollama 同時提供 `/v1/chat/completions` 等 OpenAI 相容端點（實測 `/v1/models`、
`/v1/chat/completions` 皆回 200），看起來是更「可攜」的選擇。**但相容層沒有 `think` 參數**，
而關閉思考是硬性要求（§10.8.1、定案 #25）——實測用 `/v1/chat/completions` 送
`max_tokens:32`，回來就是 `content:""` ＋ `finish_reason:"length"`，
**空字串陷阱在相容層原封不動重現，且無從關閉思考**。

→ 因此使用原生 `/api/chat`（帶 `think:false`）與 `/api/embed`。

> **抽象層仍然要有，但目的變了**：`ILlmClient`／`IEmbeddingClient` 的存在理由是
> **讓單元測試能替換掉真實推論**，不是為了日後換供應商。
> 不要為了「將來可能換」而建一套供應商框架——那個「將來」現在已經明確不會來。

#### 不變的安全要求

**Ollama 埠一律綁 `127.0.0.1:11434`。Ollama 預設沒有任何認證**——
對外開放等於把一顆能讀你 prompt 的推論服務裸露在網路上。
需要跨主機時走反向代理＋認證，**不是**直接把 `OLLAMA_HOST` 設成 `0.0.0.0`。

#### 已知落差（記錄，不在本階段解）

**若客戶的 PostgreSQL 跑在 `docker-compose.yml` 的 `postgres:16-alpine` 容器裡**，
該映像沒有 pgvector，`apt install` 也不適用（容器重建即消失）。
這類部署要開 P3，需另行決定作法（換基底映像／改用原生 PG／自建映像）。
**本規格的 P3 前提是：PostgreSQL 為主機原生安裝。** P1／P2 不受影響（不需要 pgvector）。

### 17.6 CI

現行 [`ci.yml:74,77`](../../.github/workflows/ci.yml) 跑全部單元＋整合測試。加入本功能後：

| 測試類型 | CI 行為 |
|---|---|
| 一般單元／整合測試（含新模組的） | **照跑**，不得排除 |

> nightly 若要加「有 Ollama 的 self-hosted runner」job，**不可用 `continue-on-error` 假綠**——
> 這是既有教訓（nightly 已刻意拿掉該旗標）。沒有 runner 就讓該 job 不觸發，而不是讓它紅了當沒看見。

模型下載腳本不需要任何 token（Ollama 公開模型），**要保持這樣**——一旦需要憑證，
就會有人把它寫進腳本，然後被 gitleaks 擋下（或更糟，沒被擋下）。

### 17.10 具體 git 與安裝作業程序（2026-08-05 逐檔查證守門規則）

§17.1–17.9 講的是設計與前置。本節是**操作手冊**：日後「要」與「不要」這套 Q&A／報表工具的兩種部署，
在 git 端與安裝端各自要做什麼、不做什麼。

#### 17.10.0 大前提：**不做「有／沒有」兩個版本**

同一份 repo、同一個 tag、同一份組建產物出貨，「有沒有這功能」只差**組態值**。
不採「發布時砍掉程式碼」或「另開一條 `no-llm` 分支」，理由是實測出來的：

- `Modules/` 在 [`scripts/core-drift-baseline.txt`](../../scripts/core-drift-baseline.txt) 有 **0 筆**——走模組路線的版控成本本來就是零，沒有必要用分支換取。
- 分兩條發布分支，等於每次 `update-core.sh` 都要 merge 兩次，且 `core-drift-baseline.txt` 會分岔（兩條線各自增減），**Core 漂移守門形同失效**。

**網路怎麼接——採 SSH 反向通道（2026-08-06 實測打通）**

#### 三個一次性設定

**① WSL 端的 sshd 改綁 `127.0.0.1:2222`**（`:22` 被另一個 distro 佔著，兩者共用 netns）：

```ini
# /etc/systemd/system/ssh.socket.d/override.conf
[Socket]
ListenStream=
ListenStream=127.0.0.1:2222
```

> `ListenStream=`（空值那行）**不能省**：systemd 的 `ListenStream` 可累加，
> 不先清空會保留繼承來的 `0.0.0.0:22`，重啟仍舊撞另一個 distro 而 `failed`。

**② 專用金鑰，且在 `authorized_keys` 端鎖死用途**（自動啟動的排程工作無法輸入 passphrase，
所以金鑰沒有密碼——安全性改由授權範圍承擔）：

```
restrict,port-forwarding,permitlisten="*:11435" ssh-ed25519 AAAA...
```

> ⚠️ **必須是 `*:11435` 而不是 `127.0.0.1:11435`。** `permitlisten` 比對的是
> **客戶端請求的 bind address**，而 `-R 11435:...` 送出的是**空字串**，與寫死的位址對不上，
> sshd 直接拒絕轉送（錯誤訊息只有一句 `remote port forwarding failed for listen port 11435`，
> 不會說是被授權擋掉的）。
> 放寬的只是「位址比對」——實際綁哪裡由 `GatewayPorts=no`（預設）決定，
> 實測監聽確實只出現在 `127.0.0.1` 與 `[::1]`，埠仍限死一個。

**③ Windows 端建立通道**（一般使用者，無需提權、不碰防火牆）：

```powershell
ssh -N -p 2222 -i $env:USERPROFILE\.ssh\wsl-ollama-tunnel -R 11435:127.0.0.1:11434 -o ServerAliveInterval=30 -o ExitOnForwardFailure=yes dev@localhost
```

> ~~常駐：工作排程器建「登入時執行」的**使用者層**工作，或放捷徑到 `shell:startup`。~~
> ⚠️ **2026-08-31 撤銷這條建議：觸發時機不對。** 見下方〈坑三〉。
> `ExitOnForwardFailure=yes` 讓轉送失敗立刻退出而不是靜默不轉送。

#### 三個非踩不可的坑（前兩個都花了一輪才找到，第三個花了兩次）

**坑一：通道的監聽埠不能等於目標埠。**

WSL 內只要開了 `127.0.0.1:11434`，localhostForwarding 就自動在 **Windows 的 `127.0.0.1:11434`**
開一個 `wslrelay` 鏡射——而那正好是轉送的目標：

```
Windows ssh → Windows 127.0.0.1:11434（wslrelay）→ WSL 通道監聽 → 轉回 Windows 11434 → 回圈
```

症狀是所有請求逾時或 `Empty reply from server`，而 `ss` 看起來一切正常（監聽確實建立了）。
→ **監聽埠用 11435、目標仍是 11434。** 副作用只是應用程式端組態變成
`http://127.0.0.1:11435`（正式環境同機部署仍是 11434）——那本來就是一個組態值。

**坑二：Ollama 必須維持綁 `127.0.0.1`，不可開 `Expose to the network`。**

開啟後 Ollama 改綁 `::`（IPv6 wildcard），而通道的目標是 IPv4 `127.0.0.1:11434`，
**打不到**（從 Windows 自己 `curl 127.0.0.1:11434` 也是 `000`）。
更麻煩的是那個設定會跳出防火牆授權提示，**取消後 Windows 會留下兩條
`ollama.exe Inbound Block` 規則，而刪除它們需要系統管理員權限**——這條路從此堵死。
→ 維持預設綁定即可；通道全程走 loopback，本來就不需要任何防火牆規則。

**坑三：通道是一次性的——WSL 一重開機就斷，而且不會自己回來。**（2026-08-31 補；已咬過兩次）

通道是 Windows 上一支 `ssh -N` **連進 WSL 的 sshd**。WSL 關機時 TCP 斷、該進程退出，
沒有任何東西會重拉。而 Win11 的 `ollama.exe` 反而好好的（`shell:startup` 有 `Ollama.lnk`，
開機自啟），所以**壞掉的只有中間那一段**，症狀是「模型明明在、卻連不上推論服務」。

實測時間軸（2026-08-31）：WSL 開機 `07:39:55`，通道到 `08:18` 手動拉起才恢復——**空窗 39 分鐘**。

**上面那條「工作排程器／`shell:startup`」的建議擋不住這個情形，所以已撤銷**：
那是「**Windows 登入時**」觸發，而 `wsl --shutdown` 不需要重新登入 Windows。
**觸發時機與故障時機對不上**——這是這一節真正的教訓，比「要設自啟」本身重要。
（順帶一提，那條建議從 2026-08-06 寫下後從未被執行：`shell:startup` 只有 `Ollama.lnk`、
`schtasks` 也查無相關工作。文件寫了建議、建議本身不對症、而且也沒人做，三層都漏。）

**修法：改由「app 啟動」觸發**——那才是唯一與「WSL 重開機」對得上的時機（重開機後本來就要重啟 app）。

| | |
|---|---|
| `tools/switch-llm.sh ensure` | 只確保目前 profile 的端點通，**不改組態、不碰 app**。手動復原就這一句 |
| `tools/run-app-llm.sh` | 啟動前自動呼叫上者。**刻意不致命**：拉不起來就印警告照常啟動——詞彙通道不需要任何模型（§10 的「嵌入失敗只降級、不中止」） |

> `ensure` 之所以獨立成一個子命令、而不是直接重用 `win`：`win` 會走到 `restart_app`，
> 而 `restart_app` 啟動的正是 `run-app-llm.sh`——兩者互相呼叫就無限遞迴。

**驗證方式（2026-08-31 實測）**：`Stop-Process` 殺掉通道 → `11435` 回 `000` →
`tools/switch-llm.sh ensure` → `200`。**自癒路徑沒被觀察到癒合過，就只是宣稱而不是事實。**

> ⚠️ 殺通道驗證時**不可** `taskkill /IM ssh.exe`：實測當下另有一支無關的互動 `ssh.exe`
> （連 `dev6.its.sinica.edu.tw`），照名字殺會把它一起帶走。
> 用 `Get-CimInstance Win32_Process` 看 `CommandLine`，認 `-R 11435` 那一支的 PID。

| 條件 | 實測 |
|---|---|
| Windows OpenSSH client | ✅ `C:\WINDOWS\System32\OpenSSH\ssh.exe`（Win10/11 內建，免安裝免提權） |

**為什麼是這個而不是別的**（決策依據是「本開發機沒有 Windows 系統管理員權限」）：

| 方案 | 需 admin | 需重開 WSL | 暴露面 | 判定 |
|---|---|---|---|---|
| **SSH 反向通道** | 否 | 否 | **不變** | ✅ **採用** |
| `networkingMode=mirrored` | 否（`.wslconfig` 是使用者自己的檔案） | **是——兩個 distro 一起停** | RockyLinux 的 `*:3306`／`0.0.0.0:22` 會綁上主機介面，**而無 admin 就補不了防火牆規則來收斂** | ❌ 不採 |
| `netsh interface portproxy` | **是** | 否 | 僅主機內部介面 | ❌ 無權限 |
| `OLLAMA_HOST=0.0.0.0` | 否 | 否 | **無認證推論服務開到區網** | ❌ 違反 §17.5 |
| Ollama 裝進 WSL | 否（需 WSL sudo） | 否 | 不變 | ❌ 模型落進 vhdx，違反 §17.11.2 的支點 |

**這個選擇的附帶好處**：WSL 端的組態就是一個 `http://127.0.0.1:<port>`，
與「Ollama 跑在本機」完全相同——**程式碼與設定檔不需要為開發環境做任何特例**，
日後換到正式環境（Ollama 與應用程式同機或走內網位址）也只是改一個組態值。

**代價**：通道是一個必須存活的行程，而且 **WSL 一重開機它就沒了**——
常駐作法改由 `tools/run-app-llm.sh` 在 app 啟動前呼叫 `switch-llm.sh ensure`，
**不是**工作排程器／`shell:startup`（觸發時機對不上，理由見 §17.11.2 坑三）。
`ExitOnForwardFailure=yes` 讓「port 已被佔用」立刻失敗而不是靜默不轉送——
**少了這個旗標，通道會看似連上但實際沒轉送，症狀是 Ollama 呼叫全部逾時**。

> **原方案（mirrored）的紀錄保留於此**，因為它在「有 admin 或單一 distro」的環境仍是最乾淨的解。
> 若日後改採，切換前必須先把 RockyLinux-9 的 `*:3306`／`0.0.0.0:22` 改綁 `127.0.0.1`，
> 並單獨排一次驗證（重跑 UITests :5110 ＋ 確認 PG 5432）——**不要與功能開發混在同一次改動**。

| 決策 | 內容 |
|---|---|
| **現在** | **維持同組件＋旗標**（§17.10.0）。QAA 的相依極輕——pgvector EF 套件約 200 KB，**Ollama 走 REST 連套件都不需要**。拆組件換來的「不納入」利益 < 1 MB，不值得為此動 Core |

| **對採用者的承諾** | 三句話：① 預設全關；② 不裝 pgvector、不裝 Ollama 也跑得起來；③ `QaDbContext` 的 migration 永不執行、選單不出現 |

> 這條準則的價值在於**它給了一個可檢查的觸發條件**，而不是「以後再看」——
> 每次要為 QAA 加 NuGet 套件時，問一句「這個套件會不會帶原生二進位」即可判定要不要開始拆。

| WSL 內的 Ollama | 無（模型不進 vhdx 是整套策略的支點） | **多了一份**：`~/.local/ollama`，2026-08-19 裝，`gemma3:4b` 4.2 GB **在 vhdx 內** |
| Windows 帳號權限 | 非系統管理員 | ✅ 仍然成立（實測 `IsInRole(Administrator)` = `False`） |

> 🚨 **`OLLAMA_MODELS` 指到 LM Studio 某一顆模型的子目錄，這有兩個實質風險**：
> ① **連帶刪除**——那個資料夾在 LM Studio 眼中是「gemma-4-26B 這顆模型的家」，
> 從 LM Studio 刪除該模型（或它自己清理）會把 ollama 的 12 顆 **一起帶走**；
> ② **空間**——48.9 GB ＋ LM Studio 自己的 16.8 GB 全壓在 C:（剩 109 GB）。
> 這個設定不在 User／Machine 環境變數裡（兩者皆空），是 Ollama app 自身的設定，要從 GUI 改。

> ### 🚫 搬去 D: 是錯的——**§17.11.2 的「模型放 `D:\ollama\models`」這條定案要撤銷**
>
> 該定案（2026-08-05）只看了「D: 剩 665 GB」，**沒有查媒體類型**。2026-08-21 實測：
>
> | 磁碟 | 裝置 | 循序讀取 | 載入 `gemma4:latest`（10.4 GB） |
> |---|---|---|---|
> | **C:** | Micron 2400 **NVMe SSD** 477 GB | **1128 MB/s** | **約 9 秒** |
> | **D:** | Seagate ST1000DM014 **HDD SATA** 932 GB | **199 MB/s** | **約 52 秒** |
>
> **5.7 倍差距，而且是每次冷載入都要付。** Windows 端 Ollama 預設 `keep_alive` 只有 5 分鐘，
> 開發時問完一題、去改個程式回來就已經卸載——一題 97 秒會變成約 150 秒。
> 推論本身不讀磁碟（權重在 RAM），所以 HDD **只**懲罰載入，但那正是開發迴圈最常付的成本。
>
> **正解：搬到 `C:\ollama\models`（同一顆 SSD 內）**，只解決「連帶刪除」這個真風險。
> 同 volume 移動是 metadata 操作，**秒完成、不需要複製 48.9 GB**；
> 搬去 D: 反而要跨碟真複製（HDD 寫入約 5–6 分鐘）再永久承擔載入懲罰。
> C: 剩 109 GB，模型本來就已經在 C:，搬完空間帳不變。
>
> 連帶建議：把 Windows 端的 `OLLAMA_KEEP_ALIVE` 調長（WSL 那份的單元檔已設 30m），
> 減少冷載入次數——這比換磁碟有效得多。

##### 這台有兩份 Ollama，而且都綁 11434

**最容易誤判的前提**：兩份都綁 `127.0.0.1:11434`，但在**不同 network namespace**。
從 WSL 打 `127.0.0.1:11434` **永遠**打到 WSL 那份，打不到 Win11 那份。
→ 「連得上」不等於「連對了」，症狀會是「明明 Win11 有 `gemma4`，卻回報模型不存在」。

| | WSL 側 | Win11 側 |
|---|---|---|
| 位置 | `~/.local/ollama`（模型在 vhdx 內，違反 §17.11.2 的支點） | `%LOCALAPPDATA%\Programs\Ollama` 0.32.6 |
| **從 WSL 的位址** | `http://127.0.0.1:11434` | `http://127.0.0.1:11435`（SSH 反向通道，§17.11.2） |
| 模型 | 只有 `gemma3:4b` | 12 顆，含定案 #44 的 `gemma4:latest` |
| 記憶體 | WSL 15 GB | 約 31 GB（`.wslconfig` 沒分給 WSL 的那部分） |

**定案（2026-08-21，使用者裁決）：Win11 那份為主力，WSL 那份保留但取消開機自啟。**
已 `systemctl --user disable ollama.service`；單元檔留著，由切換腳本按需 `start`。
理由：模型庫、可用記憶體都在 Win11 側，且 WSL 那份的模型佔著 vhdx（vhdx 只增不減，§17.11.5）。

問題：既然端點已經可切（§17.11.7），能不能再多一個「切到外部 LLM」的 profile？

**先講結論：技術上成本很低，但它不是技術問題。**
`switch-llm.sh` 那層只是換一個 URL，真正要裁決的是**資料出境邊界**，而那已經有既定立場。

##### 一、技術面：介面夠窄，不需要長供應商框架

`ILlmClient.ChatAsync(systemPrompt, userPrompt, ct)` 只吃兩個字串、回一個 `LlmAnswer`
——**接任何供應商都不難**。但 §17.5 有一條相反方向的既有裁決要先面對：

> 「三個介面刻意分開，但只有一個實作。它們存在的理由是讓單元測試替換掉真實推論，
> **不是**為了日後換供應商——不要據此長出一套供應商框架。」

這條**不必推翻**：多一個 provider 不等於長框架，前提是**只加一個實作、不加抽象層**。
一旦開始寫「供應商能力矩陣」「參數轉譯器」就是走偏了。

**三個具體的技術代價**：

| # | 代價 | 說明 |
|---|---|---|
| 1 | **`think` 參數沒有對應** | §17.5 定案「走原生 API 不走 OpenAI 相容層」，唯一理由就是相容層**沒有 `think`**，而關閉思考是硬性要求（實測 528 tokens／43.4 秒 → 58 tokens／4.7 秒，**9 倍**）。外部供應商各家關思考的方式都不同（有的靠參數、有的靠模型版本、有的關不掉）。→ 外部 provider 必須**各自**在 client 裡處理，且**必須逐顆重測 §10.8.1 的生成契約**，不能假設 |
| 2 | **嵌入不能跟著換** | 換 `IEmbeddingClient` 的供應商＝換向量空間＝**全量重嵌**（§10.7 已有 `DocChunk.EmbeddingModel` 守門）。外部嵌入還是逐次計費、有速率限制，而索引重建是 1114 chunks 起跳。→ **建議：外部 provider 只換生成，嵌入永遠留在本地。** 這也讓 §17.11.7 守門 3 繼續有效 |
| 3 | **失敗形狀變了** | 目前的降級路徑（§10.8、§17.8）假設推論服務在本機：不通就是不通。外部供應商多了逾時、限流、額度用盡、供應商停用模型——**這些都是「時好時壞」而不是「壞掉」**，是最難查的形狀 |

##### 二、真正的阻擋：資料邊界，且 Phase 1 與 Phase 2 完全不同

| | 送出去的是什麼 | 評估 |
|---|---|---|
| **Phase 1（手冊 Q&A）** | 使用者提問 ＋ 檢索到的**手冊／擷取物**片段 | 語料是**內部級**產品文件，不含營運資料。風險可控，是**唯一適合先開的範圍** |
| **Phase 2（NL 查詢營運資料）** | 使用者提問 ＋ **真實營運資料**（工具回傳的列） | 🚨 **§八已裁決「含金額＝機密」（28 支，定案 #2）**。把它送到外部供應商，等於讓資料繞過 §8.4 分層防線、§8.5 彙總洩漏控制、§8.6 稽核——**那整章的前提就是推論在內網** |

> **所以這不是「要不要接外部 LLM」，是「接了之後 Phase 2 怎麼辦」。**
> 若沒有硬性閘門，Phase 2 一開燈，機密資料的出境管道就自動存在了，
> 而且它比 §8.1 記錄的 `CanPrint` 缺口更難察覺——那至少還在自家系統內。

##### 三、還有一個部署面的理由

§17.11.6 對採用者的承諾是「**不裝 Ollama 也跑得起來**」。外部供應商引入的是相反的東西：
**必須有 API key、必須能對外連線**。工廠的 ERP 伺服器**不對外**是常態，
且金鑰管理（輪替、外洩、誰的帳單）在本專案完全沒有基礎設施。
→ 外部 provider 只能是**選配的選配**，絕不可成為預設或前置。

##### 四、若要做，建議的形狀（**尚未裁決，不要據此實作**）

1. **`Features:QaAssistant:Provider` = `ollama`（預設）｜ `openai-compatible`**，與端點同一層，不新增抽象層。
2. **分兩類，不要混為一談**（⚠️ **2026-08-21 更正**：本項原本寫「一律走 OpenAI 相容層、一個實作打天下、不必加 NuGet」，**對自架服務成立，對商用雲端 API 不成立**，見 §17.11.8-五）。
3. **嵌入永遠留本地**（代價 2）。
4. 🔒 **硬性程式閘門**：`Provider != ollama` 時，Phase 2 的工具層一律拒絕執行並記稽核——
   **寫成測試守住，不是文件約定**。這一條是本項能否成立的**前提**，不是附帶條件。
5. 金鑰只從環境變數讀，**永不進 `appsettings*.json`**（該檔會被還原、會進備份，且 gitleaks 只擋得住進版控的那一份）。

**需要裁決的是第 4 條的範圍**：外部 provider 是「只准 Phase 1」，
還是「Phase 2 也准，但排除 28 支機密報表」。前者簡單且守得住，後者等於把 §八 的判斷
搬到一個新的維度上再做一次。→ **建議前者。**

##### 五、「能用不同的 LLM 嗎」——分三類，成本與作法天差地遠

**這三類常被當成同一件事，實際上只有前兩類是「換個 URL」。**

| 類 | 對象 | 換法 | 成本 |
|---|---|---|---|
| **A** | 同一個 Ollama 換模型（`gemma4:12b`、`llama3.1:8b`、`phi4`…） | `switch-llm.sh win <model>` | **已具備**（§17.11.7），零程式碼 |
| **B** | 其他**自架** OpenAI 相容服務：vLLM、LM Studio（`lms server`）、llama.cpp server、LiteLLM proxy | 換 URL ＋ 走 `/v1/chat/completions` | 低。**「一個實作打天下」只在這一類成立** |
| **C** | **商用雲端 API**：Claude、GPT、Gemini | ❌ **不能只換 URL** | 見下 |

**C 類為什麼不能只換 URL**（這推翻了本節第四段原本寫的第 2 條）：

各家都有 OpenAI 相容端點，但那是**過渡用途的最小交集**。以 Claude 為例，走相容層會失去
adaptive thinking、`effort` 控制、prompt caching 的細部放置、server-side tools ——
而本專案對推論的**唯一硬性要求就是控制思考行為**（§10.8.1：關掉思考是 9 倍差距）。
更麻煩的是那個要求在 Claude 上**語意完全不同**：Claude Opus 5 預設就開 adaptive thinking，
`thinking:{type:"disabled"}` 在 `effort` 高於 `high` 時直接回 400，
官方作法是**用低 `effort` 取代關閉思考**。→ **「把 `think:false` 照搬過去」是行不通的**，
每一家都要各自實作並**逐顆重跑 §10.8.1 的生成契約與 §10.8.2 的品質評測**。

C# 專案接 Claude 的正解是官方 `Anthropic` NuGet（純受控組件、不帶原生二進位，
故不牴觸 §17.11.6），**不是** OpenAI 相容 shim。

##### 六、適用條件：分開「開發期工具」與「產品功能」，這是本評估最重要的一刀

**✅ 立刻適用、而且不需要待決 #49 的裁決——開發期評測**

§10.8.2 那種評測（六顆候選 × 53 題）在本機 CPU 上是 **97 秒／題**，一輪要好幾小時；
換模型、改提示詞都要重跑一輪。外部 API 是幾秒一題。關鍵是：

> **評測餵進去的是手冊內容與題庫，不是營運資料**——完全不觸及 §八 的機密邊界，
> 而且它是**開發工具**不是產品功能：不進產品程式、不影響部署、客戶端完全無感。
> → 這一項可以現在就做，**不必等 #49 裁決**。

同理適用：用強模型（`claude-opus-5`）當 **judge** 評分生成品質、或協助擴充難題題庫（定案 #40）
——這兩件事目前都靠人工判讀，是評測迴圈的真正瓶頸。

**⚠️ 需要裁決——產品功能（Phase 1 的線上問答）**

送出去的是使用者提問＋手冊片段（內部級）。技術上可行，但要接受金鑰管理、
出境連線、以及「失敗形狀從『不通』變成『時好時壞』」。

**🚫 不適用**

| 情境 | 理由 |
|---|---|
| **Phase 2 營運資料** | §八 裁定含金額＝機密（定案 #2，28 支）。**這是本評估的紅線** |
| **客戶自架、不對外的 ERP 伺服器** | 工廠常態。§17.11.6 承諾「不裝 Ollama 也跑得起來」，不能變成「不給 API key 就跑不起來」 |

##### 七、作法：兩條路，強烈建議先走第一條

**路徑一：開發期評測工具（建議現在就做，零產品風險）**

不動任何產品程式。獨立腳本／測試專案直接呼叫外部 API，讀**同一份題庫與同一份手冊語料**，
輸出與現行評測相同格式以便對照。金鑰只從環境變數讀。
產出的是「本地 `gemma4:latest` vs 雲端模型」的品質基準線——
**這條基準線目前不存在**，而沒有它就無法回答「本地模型到底夠不夠好」。

> **✅ 2026-08-24 已實作。**`SmartFactory.MES.IntegrationTests/QA/EvalLlmClients.cs`
> （`EvalLlmClients`／`AnthropicEvalClient`／`OpenAiCompatibleEvalClient`），
> 守門測試 `EvalLlmClientTests`（17 支，**不打網路**）。
>
> ```bash
> # 本機（預設，行為與從前完全相同）
> QA_LIVE_OLLAMA=1 dotnet test --filter 量測_生成品質的四項指標
>
> # 雲端（Anthropic）；嵌入仍走本機 Ollama，故 QA_LIVE_OLLAMA 仍要 1
> QA_LIVE_OLLAMA=1 QA_EVAL_PROVIDER=anthropic QA_EVAL_MODEL=claude-opus-5 \
>   QA_EVAL_API_KEY=… QA_EVAL_EXTRA_JSON='{"thinking":{"type":"disabled"}}' \
>   dotnet test --filter 量測_生成品質的四項指標
>
> # 自架 OpenAI 相容（vLLM／LM Studio／llama.cpp／LiteLLM）
> QA_LIVE_OLLAMA=1 QA_EVAL_PROVIDER=openai-compatible \
>   QA_EVAL_BASE_URL=http://10.0.0.20:8000 QA_EVAL_MODEL=qwen2.5:14b \
>   dotnet test --filter 量測_生成品質的四項指標
> ```
>
> 四個設計決定：
> ① **判定程式碼一行未動**——`ManualGenerationBenchmarkTests` 只改「解析哪個 client」
> 與報表抬頭；抬頭一定印後端，否則兩份報表分不出是換了模型還是換了機器。
> ② **關思考的寫法不寫死**（`QA_EVAL_EXTRA_JSON` 併進請求本體）：§10.8.1 要求控制思考
> （9 倍差距），但各家做法不同且會變——Claude 的 adaptive thinking 預設開啟，
> `thinking:{"type":"disabled"}` 在 effort 高於 high 時直接回 400，官方作法是改用低 effort。
> 寫死的話過期症狀是 400 或悄悄多花十倍 token。
> ③ **截斷與空答案一律當失敗**，與本地對 `done_reason=="length"` 的處置一致：
> 判準不同的話「被截斷」會在雲端算成功，而截斷的答案通常只少了最後一行來源，看起來完全正常。
> ④ **只取 `text` 區塊**，`thinking` 不算答案——混進來會讓幻覺引文率變成雜訊，
> 而那是四項指標裡唯一完全可自動判定的一項。

##### 八、已落地的閘門：`IInferenceEgressPolicy`（2026-08-24）

**它補的不是「接了外部 LLM 之後」的洞，是今天就開著的那個洞。**

`OllamaClient.ResolveBaseUrl` 對 `Features:QaAssistant:OllamaUrl` 只驗「是不是合法絕對網址」、
不限主機，而 Phase 2 會把 §八 裁定為機密的營運資料整列送進推論服務。
`switch-llm.sh`（§17.11.7）讓改端點只是一行指令。
`AllowMonetaryTools=false` 看起來像有保護，但它管的是**問得到什麼**、不是**資料流去哪裡**
——兩者只在預設值下巧合疊在一起。

| 面向 | 決定 |
|---|---|
| **判準** | 端點是 loopback → 放行；否則主機必須明示登錄在 `Features:QaAssistant:TrustedInferenceHosts`（可寫 `host` 或 `host:port`；環境變數用逗號分隔）。**內網也擋**——閘門管的是「送不送得出這台機器」，放寬成「私有網段自動信任」的話，一台被接進同網段的機器就自動取得機密資料 |
| **範圍** | **只擋 Phase 2**（`QaToolQueryService.AskAsync`／`ConfirmAsync`）。Phase 1 手冊問答不受任何約束——它送的是產品手冊（內部級），把兩者綁死會讓「換一台機器跑推論」這件正當的事變成不可能 |
| **落點** | `AskAsync` 的**最前面，連 schema 都不組**：選工具那一次送出去的是使用者的提問，而提問本身就可能寫著客戶名與料號。擺在「執行工具之前」等於已經漏了一次。`ConfirmAsync` 另外重驗一次（端點可能在兩輪之間被改掉，與重跑權限檢查同一個理由） |
| **判定時機** | 啟動時一次，singleton，且**與具名 `HttpClient` 的 `BaseAddress` 讀同一份 `IConfiguration`**（工廠閉包捕捉 `RegisterServices` 階段那一個）。每次呼叫重讀會出現「閘門依新 URL 放行／擋下，而 HttpClient 還在打舊的」——稽核紀錄與實際去向不一致，最難查 |
| **出聲** | 判定結果進啟動日誌（§17.8）。singleton 是延遲建立的，所以 `Configure` 刻意解析它一次；否則「Phase 2 已停用」要等第一個人提問失敗才有人知道 |
| **稽核** | 被擋下的嘗試**要寫進 `QaTurn`**（`Outcome=EgressBlocked`）。「被擋下」與「沒人問過」是兩件事，而事後要回答「那段期間有沒有人試圖用 NL 查營運資料」只能靠它 |
| **訊息** | 新增 `QaEgressBlocked`（雙語）。指向**組態**不指向使用者：他有權限、問法也沒錯 |

⚠️ **它擋不住什麼**：loopback 可能是一條 SSH 通道（開發機的 `localhost:11435` 正是通到 Windows 端）。
閘門看不穿通道，也不該假裝看得穿——它擋的是「改一個 URL 就靜默送出去」，
主機層的出境控制要靠防火牆。**現行兩個來源（WSL `11434`、通道 `11435`）都是 loopback，零組態即通過。**

守門測試：`InferenceEgressPolicyTests`（10 支）＋ `QaToolQueryServiceTests` 三支
（提問不送去推論／被擋下要進稽核／兩輪之間被改掉時收掉待確認那一列）。
