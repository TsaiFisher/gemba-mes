## 1. 資料稽核儀表板（每個 Wave 的收尾工具）

人工測試最大的浪費是「畫面點得動就算過」。系統已內建 17 支資料稽核，
把判準從「能操作」升級成「帳對得起來」，每個 Wave 收尾都要用。

### 1.1 操作方式

| 項目 | 內容 |
|---|---|
| 畫面位置 | 選單 MenuKey `DataAudit`（報表/分析類），路徑 `/DataAudit` 或 `/RPT/DataAudit` 視選單登錄而定 |
| 檢視權限 | 該選單的**讀取**權限，缺少時 `Index` 直接回 403 |
| 執行權限 | 該選單的**異動（Update）**權限。缺少時畫面**不會顯示**「立即執行稽核」按鈕（`ViewBag.CanRunNow`），且直接 POST 也會被擋 |
| 手動觸發 | 畫面上「立即執行稽核」按鈕 → `POST /DataAudit/RunNow`（帶 AntiForgery Token） |
| 執行範圍 | `plantId: null` = **全廠稽核**，不受目前登入廠別限制 |
| 結果呈現 | 明細表**只顯示目前登入廠別 + 無廠別維度**的異常。多廠測試時**每個廠別都要各自登入查看**，否則會漏看 |
| 結果保存 | 每次執行寫入 `DataAuditRuns`（觸發方式/耗時/異常數）與 `DataAuditFindings`（異常明細），**保留 90 天** |
| 自動執行 | `DailyDataAuditJobService` 每天 02:00（伺服器時區）自動跑一次，`TriggerType='Scheduled'`、`CreatedBy='SYSTEM'` |
| 畫面內容 | KPI 卡 + 近 30 次異常趨勢圖 + 異常明細表（可依稽核類型篩選） |

程式位置：[DataAuditController.cs:41](../../Modules/RPT/Controllers/DataAuditController.cs#L41)（Index）、
[DataAuditController.cs:53](../../Modules/RPT/Controllers/DataAuditController.cs#L53)（RunNow）。

### 1.2 測試人員的標準用法

1. **每個 Wave 開始前**跑一次並記下異常數 → 這是本梯次的基線（可能有前次遺留的髒資料）。
2. **每個 Wave 結束後**再跑一次 → **異常數必須回到基線或更低**，任何新增異常都要判讀處理完才算通過。
3. 判讀時看 `DataAuditFinding` 的四個欄位：`AuditType`（哪一支稽核）、`DocId`（哪張單）、
   `DifferenceAmount`（差異金額）、`ErrorDescription`（說明）。
4. 若手動觸發後畫面沒有預期的異常，先確認是不是**登入廠別不對**（見上表「結果呈現」）。

### 1.3 17 支稽核與對應的 Wave

| 稽核類型 | 檢查內容 | 主要在哪個 Wave 生效 |
|---|---|---|
| `PO_OVER_RECEIPT` | 採購超收 | Wave 1、4 |
| `GRIR_OVER_INVOICE` / `GRIR_AGING` | GR/IR 暫估超開發票、暫估滯留 | Wave 1 |
| `AuditJournalBalance` | 傳票借貸不平 | 全部 |
| `AuditDuplicateJournal` | 重複立帳 | Wave 4 |
| `INV_ROLLFORWARD` | 庫存滾動平衡（期初+進-出=期末） | 全部 |
| `AuditOrphanPosting` | 孤兒過帳（單據已刪但過帳仍在） | Wave 4 |
| `AuditPoReceivedQtyDrift` / `AuditSoShippedQtyDrift` | 反正規化累計量漂移 | Wave 1、3、4 |
| `OUTSOURCE_NEG_BALANCE` | 委外在外原料負餘額 | Wave 2（委外） |
| `BACKFLUSH_MISMATCH` | 後沖料消耗與報工不符（不分後沖時機） | Wave 2 |
| `WO_MATERIAL_NOT_ISSUED` | 工單已入庫但 Push／Pull 用料一顆都沒領 | Wave 2 |
| `AuditWipSnapshotConsistency` | WIP 期末快照一致性 | Wave 2、5 |
| `WO_COST_JOURNAL_DRIFT` | 逐工單成本與傳票回溯不符 | Wave 2 |
| `AuditShipmentInvoiceGap` / `AuditSoOverShipment` | 出貨未開票、超出貨 | Wave 3 |
| `SALES_RETURN_COST_DRIFT` | 銷退入庫成本 ≠ 來源出貨成本 | Wave 3 |
| `ERP_SYNC_LAG` | ERP 拋轉滯留 | Wave 5（若啟用外部 ERP） |

> **關帳擋關**：`AccountingPeriodService.ClosePeriodAsync` 在寫入 Closed 前會跑一次全稽核，

> 第一件事是回頭看稽核異常，不是懷疑月結功能壞掉。

## 2. 測試環境與資料紀律

| 項目 | 要求 | 原因 |
|---|---|---|
| 資料庫 | 使用**測試專屬資料庫**，不與自動化測試、效能量測共用 | 測試庫名在整合測試中寫死，跨進程沒有任何保護，會互相洗掉資料 |
| 廠別 | 至少建立**兩個廠別**，一個主測、一個只用來驗證隔離 | 資料權限與多廠隔離缺陷只有兩廠並存才看得出來 |
| 批次識別 | 每一輪測試的單據，在備註或自訂欄位標上批次代號（如 `W1-0816`） | 稽核報異常時才回溯得到是哪一輪、哪張單造成的 |
| 料號 | 固定一組測試料號，**至少涵蓋**：整數單位料、小數位單位料（如 KG 三位小數）、外幣採購料、有 LotNo 管制料 | 精度與多幣別是最容易漂的兩處 |
| 帳務期間 | 開立**兩個以上會計期間**且保持 Open | Wave 4 要測期間鎖，Wave 5 要測月結，只有一個期間跑不完 |
| 快照 | 每個 Wave 通過後**備份一次資料庫** | Wave 失敗時可回退，不必從頭建主檔 |
| 記錄 | 每個步驟記錄：單號、操作人、預期結果、實際結果、稽核前後異常數 | 缺陷回報沒有單號等於無法重現 |

### 8.4a 5-4 剩下的那一半：PWA 實機測試細節（2026-09-24 擬定）

**相機掃描與實機操作業主已於 2026-09-10 前後實機確認通過**（口頭回報，當時未留存執行紀錄）。
於是 5-4 剩下的人工範圍收斂成一件事：**PWA 本身**——安裝、離線冷啟動、版本更新、推播。
這一節寫的是拿著手機要按哪些鍵、看到什麼才算過，以及**哪些難看的行為是已知的、不要當成新缺陷**。

#### 為什麼這一塊機器測不到

`UITests/Mobile/MobilePwaOfflineTests` 那 4 支在真的 Chromium 裡註冊真的 SW、真的斷網，
釘的是 **SW 的行為**（預快取完整性、`ignoreSearch`、離線替代頁、快取保留清單）。
它碰不到的是四件事，而這四件正好是「PWA」這個詞真正的內容：

| 機器碰不到 | 為什麼 |
|---|---|
| **安裝**（加到主畫面） | Playwright 不會安裝 PWA。manifest 的圖示、`display`、`start_url` 在分頁裡完全不生效 |
| **standalone 視窗** | 沒有網址列、沒有瀏覽器的上一頁。導覽走錯只能靠頁面自己的按鈕救，分頁裡永遠測不出這個約束 |
| **推播** | 推播是**伺服器打 FCM／APNs**，再由作業系統叫醒 SW。headless 沒有作業系統通知中心 |
| **iOS / WebKit** | Playwright 跑的是 Chromium。Safari 的 SW、通知、儲存分區規則與 Chrome 不同，且只有 iOS 要求「**先安裝**才可能有推播」 |

#### 硬前置（缺一項這一節就做不了）

| # | 前置 | 判準／怎麼確認 |
|---|---|---|
| A | **憑證鏈乾淨** | ⚠️ 手動點掉憑證警告**擋不住**：Chrome 對 Service Worker 有 secure context **之外**的額外限制，憑證鏈有錯一律拒絕註冊（相機、登入 cookie 反而照常，所以很容易誤判成「環境沒問題」）。要嘛裝自建 CA（`CA:TRUE`＋`keyCertSign`、SAN 含 IP、`-days ≤ 398`），要嘛走 Cloudflare Tunnel（公開 CA，手機免裝）。裝置政策禁裝 CA 時只剩 tunnel |
| B | **origin 全程不變** | tunnel 每次重啟就換網址＝換 origin，**SW、快取、佇列、推播訂閱全部重來**。P-5（版本更新）跨越兩次部署，中途換 origin 等於白測 |
| C | **伺服器出得去外網** | 推播是伺服器主動打 FCM／APNs。內網孤島環境 P-7 整組跳過，不要記成失敗 |
| D | **VAPID 公私鑰成對** | ✅ **2026-09-24 已驗**：由 `appsettings.Development.json` 的私鑰推導出的公鑰，與 `appsettings.json` 的 `VapidPublicKey` 逐字相同。不成對的症狀見 P-7：訂閱成功、推播永遠不到，而畫面一個字都不會提 |

#### 先講清楚斷線時的範圍，否則這一輪會報出一堆假缺陷

> 📍 **2026-10-12 改版（SW v30）**：「離線作業」已改為「**斷線保護**」（mobile-pwa.md §5.0）。
> 原本這裡的表格（「已開著的頁面才能離線」「盤點不能離線」）與 10-05／10-09 之後的實作都不一致，已整段改寫。

**手機版需要連線才能使用。** 讀取一律即時打伺服器，連不上就顯示「需要連線」（同頁只提示一次），**不會出現舊資料**。
斷線保護只處理「按下送出的那一刻剛好斷線」：

| 斷線時做得到 | 斷線時做不到（預期行為，不是缺陷）|
|---|---|
| 送出報工、完工並報工、下工、機台狀態、上架、下架、盤點、工單發退料、備料移入、領退料申請 → 暫存手機 | 任何畫面的**資料載入**（派工、庫存、待檢單…）→「需要連線」|
| 恢復連線後自動補送（`online` 事件，另每 60 秒自動再試）| 登入、上工、FPI／IPQC／IQC、委外收料 |
| 冷啟動到殼層與首頁待送出清單（沿用 8 小時內確認過的身分）| 簽核——**刻意**不排隊（`offline-queue.js` 擲錯並有 jest 釘住）|
| Wi-Fi 有訊號但伺服器連不到時也會暫存（不只飛航模式）| 暫存超過 30 分鐘的項目**不會自動送**，要本人在待送出清單「確認送出」或「捨棄」|

四件都補了讀原始碼的守門（`MobilePwaShellTests` 4 支 ＋ `MobileServiceWorkerTests` 1 支），

> **為什麼 ①③④ 能用讀程式的方式推出來、②不能**：①③④ 的判準是「順序」與「作用域」，

### 10.2 Wave R：報表工具三頁（2026-09-10 補列）

**這一批的由來**：使用手冊有〈報表排程〉〈報表收件匣〉〈排程執行紀錄〉三頁，但這份計畫全文搜

**為什麼漏得這麼徹底**：`Features:ReportTools:Enabled` 預設 `false`，而且兩份 `appsettings*.json`

#### 補 R-3 側面板時撞到的一件（2026-09-17）

**`Assert.Contains(name, listed)` 是一個恆為真的斷言。**
「存檔後清單看得到新那一列」最直覺的寫法是把排程名稱丟進 Index 搜尋、再問回應裡有沒有那個字串——
但 `searchTerm` **會回顯在搜尋框裡**，所以無論那一列在不在，字串都在。

突變驗證撞出來的：把 `ApplyAsync` 的 `definition.ScheduleKind = model.ScheduleKind` 改成 `null`
（那一筆就成了常用查詢，排程清單再也列不到它），**這一支照樣綠**。
改成定位到表格列本身（`<td class="fw-medium">{name}</td>`）才有區辨力，
並把「它真的存成排程」分成資料層的另一道斷言——列得出來要是因為存對了，不是因為別的巧合。

🚨 **這與 R-F4 是同一個形狀**：「收得到檔案」不等於「檔案有內容」，
「頁面上有那個字」不等於「清單有那一列」。搜尋條件、標題、麵包屑、隱藏欄位都會把要找的字
印回頁面上——**在一份完整的 HTML 裡找一個字串，幾乎總是找得到**。

另外兩件順帶記下來：

- **一律回整頁也不會紅。** 把 `FormView` 的 `IsAjax` 分流拿掉（永遠 `View(...)`），
  HTTP 還是 200、欄位也都在，但那一整份含 `<html>`、導覽列與 layout script 會被塞進
  offcanvas——畫面上是爆掉的版面而不是任何一種錯誤。這一條是**突變前的思想實驗**補上的

#### R-2 的「立即生效」：本來排成人工，其實是可自動化的（2026-09-24）

**先查證再動手**：權限路徑上**沒有任何快取**——`PermissionService` 每次都查
`MenuPermissions`，`UserContext.ActiveRoleId` 每個請求重讀使用者，權限也沒有被烘進
登入 cookie 的 claims。所以「立即生效」在目前結構下是必然成立的，那正代表它該用測試釘住，
而不是每次改版叫人再點一次。

**既有四支為什麼涵蓋不到**：它們都在**請求之前**就把權限改掉了，所以就算系統在登入時
把權限烘進 cookie、或在行程裡快取一份，那四支依然會綠。新增的
`R2_權限在同一個連線上調整後_下一個請求就要生效` 在同一個已登入的連線上
**先成功打開一次**（預熱任何可能的快取）→ 撤銷 → 下一個請求必須 403 →
再授予 → 下一個請求必須 200。

**兩個方向都驗是刻意的**：只驗撤銷的話，「撤銷後永遠擋住」這種同樣錯誤的實作會通過。

**突變驗證兩次，第二次才是重點**：
- 突變①（加一層行程級權限快取）→ 紅 3 支，**既有測試也會紅**，所以這一種本來就擋得住。
- 突變②（只記住否定結果，之後再授予也不放行）→ **只紅新這一支**，四支既有測試全部看不見。

**為什麼值得釘一個目前必然成立的性質**：「為權限查詢加一層快取」是效能調校時極可能
出現的改動，而它的失效方式是**沉默的**——撤掉的權限在快取過期前仍然通行，
而管理者在矩陣上看到的是已經關掉的開關。
